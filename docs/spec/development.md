# Development conventions (gates, selftest, terminology, distribution)

Running the gates and what each one checks, the selftest conventions, the terminology for naming these concepts, and how the distributable is built.

## Running the gates

After making a change, run `scripts/check.sh` (**anyone may run it** -- see "Don't restrict who runs the gates" below for why). It runs the following gates against the whole repository, printing one result line per gate, and exits non-zero if even one fails.

```sh
scripts/check.sh
```

**This table is maintained by hand -- no gate checks it against the implementation.** The canonical list of gate names is what `scripts/check.sh --gate` prints when it's handed a name it doesn't know: it exits 2 and enumerates every selectable name. Read that output when the exact set matters; read the table below for what each one covers.

| Gate | Scope |
| --- | --- |
| `shellcheck` | All shell scripts (`*.sh`, plus files whose shebang names a shell -- independent of extension) |
| `jq` | Syntax validation of every `*.json` |
| `plugin` | **Content** validation of the plugin manifest, the hooks registration table, the marketplace registration table, and skill frontmatter |
| `docs-links` | Existence of every relative link's target (`[text](target)`) across all `*.md` in the repository, and that link text is never a path string (containing `/`, ending in `.md`) |
| `shell-quote` | That a path embedded in a ready-to-run command shown to the user has passed through `rein_shell_quote` |
| `lineage-cmd` | That a rein command shown to the user as a "type this one line" instruction has passed through the shared function that fills in the lineage naming with its effective value (`rein_lineage_cmd`; the `config` verb uses `rein_config_lineage_cmd`) |
| `self-path` | That its own location (where its bundled library lives) is never determined from an external command's output |
| `self-lib` | That the bundled library's location is never assembled from the output of an external command (`dirname` / `basename` / `realpath` / `readlink`) |
| `launcher-exec` | That the launcher the plugin's hooks call (`hooks/rein-hook-launcher.sh`) never starts the runner with `exec` |
| `run-limit` | That external processes (`claude` / `osascript`) are never started outside the capped runner (`rein_run_limited` / `rein_run_capture`) -- counted not only right after a statement separator but also a form prefixed with a condition (`if` / `!` / `while`, etc.) |
| `home-base` | That a location's base is never built by spelling out `${HOME:-}` directly, but through the shared predicate (`rein_xdg_base`) or a check that keeps it from collapsing |
| `record-append` | That a writer appending to a record checks its write target's shape (`rein_dest_shape_ok`) **before the append, in that same function** |
| `test-side-scope` | That a test-side name (a function starting with `st_` / `rein_st_` / `fake_`, or `selftest`) is never called from a production location |
| `stop-order` | That output for a blocked stop (`block`) is emitted before it's recorded to the fire log |
| `flag-value` | That parsing a value-taking flag rejects a missing value with a reason, before the branch's `shift 2` |
| `section-table` | That every `*.sh` in a check directory with a section table (`*/selftest/`) is registered in that table |
| `gate-table` | That every `gate_*` implementation in `scripts/check.sh` (a function naming its own result line via `local gate="<name>"`) is registered under the same name in the gate table |
| `dist-author` | That the distribution metadata's author name agrees (`plugin.json`'s `author.name`, `marketplace.json`'s `owner.name`, `LICENSE`) |
| `scan-source` | That the scan target in the real repository is the set git manages, i.e. `.gitignore` is actually in effect. `SKIP` on a machine without git, or where the scan root isn't the git working tree's root |
| `selftest` | Runs every executable script's (everything outside `lib/`) `--selftest` in one batch, verified down to the summary line |
| `bash32` | Runs the same `--selftest` again on the real bash 3.2 binary (`/bin/bash`) |

- **This gate layer looks only at the text, never at meaning.** Each gate reads its target file as a sequence of lines and counts only whether a fixed spelling appears in a fixed position -- the position of a command, right after an option, or a function's internal ordering. None of them check whether a value is valid, whether a code path actually runs, or whether two spellings refer to the same thing. So a form that does equivalent harm but doesn't match slips through untouched: **putting the spelling in a variable, routing it through an intermediate variable before use, wrapping the line with `\`, or using a spelling the table doesn't list**. **Read green as "no matching text was found," not as "every convention was met"** -- what these gates can't catch by text has to be caught elsewhere, by selftest (actual behavior) and by the design itself.
- **The scan target is "what gets distributed" -- the set git manages** (tracked files plus untracked files that aren't ignored). Copying the ignore list (`.gitignore`) into the check side would put it in two places that inevitably drift apart, and the moment this repository is used the way the README recommends (running `rein init` / `rein up` in a target project), `<cwd>/.rein/` (where lineage records and the handoff document live -- not a deliverable) falls inside the scan target. Once it's in, free-form prose there doesn't just turn `docs-links` red -- **the contents of a handoff document written for a different project get quoted verbatim into the FAIL output**. For the same reason that "Distribution" below never just compresses the working tree as-is, the check and the distribution look at the same set. Untracked-but-not-ignored files are included (mirroring `git archive`'s "tracked only" would put any new file not yet `add`ed outside every gate's reach, defeating the whole point of **running the check before committing**).
- **A machine without git, and a scan root that isn't the git working tree's own root (a selftest fixture -- a temp directory) both fall back to `find`.** A run that falls back isn't reading `.gitignore` -- it's checking a different set -- so **the scan-root line states which one ran** (the set is never swapped silently). If the fallback became the norm and nobody noticed, the `scan-source` gate stops it on the real repository.
- `plugin` checks: `.claude-plugin/plugin.json`'s `name` (must be `rein`); `hooks/hooks.json` (that it exists, its three-level shape, `type=command` and `timeout`, **that the registered command calls the launcher inside the plugin, wraps that path in double quotes, and that the target is executable** -- why the quoting is required is under "Registration" in [the hooks specification](hooks.md) -- **coverage of all four events** [`PostToolBatch` / `Stop` / `SessionStart` / `UserPromptSubmit`], and **that `PostToolBatch` carries no matcher**); `.claude-plugin/marketplace.json` (that it exists, its required fields, and that the plugin name matches); and `skills/*/SKILL.md` frontmatter (`name`, `description`) **plus that its usage example invokes `rein` from `PATH`**.
- `plugin` does content validation, not just syntax, so it catches changes that a syntax-only `jq` gate would let through (and it does this without depending on the `claude` CLI).
- `docs-links` excludes three things: external URLs, same-document anchors, and text inside code fences and code spans (so an illustrative example is never read as a link).
- `shell-quote` **scopes its allowlist of already-quoted variables inside each function** (a file-wide allowlist would let an unquoted variable of the same name pass just because one spot in production quoted it). The scan checks `awk`'s exit code too, so a scan that itself failed never looks the same as "zero violations."
- `lineage-cmd` counts **a bare `rein <verb>`** (`init` / `up` / `down` / `request` / `snooze` / `status` / `doctor` / `prune` / `config`). It counts not only the verb appearing right after `rein`, but also **a form with an option wedged between `rein` and the verb** (`rein --cwd <value> config allow`) -- missing that form would put any message that wrote even one common option entirely out of reach. Only a word shaped like an option (`-x` / `--xxx`) plus its one-word value can be wedged in; no other word can, so an argument list passed to the shared function is never counted as a violation. Excluded: comment lines, `case` branch pattern lines, `st_expect_not_contains` lines, and any line declared exempt with `lineage-cmd-exempt: <reason>` on the same line. Declared exemptions fall into four kinds -- a message shown before rein is on `PATH` yet, a description of something that already happened, a message that collapses **a different lineage**, and the argv sequence a test expects -- none of which are "the one line to type." The last kind isn't excluded by name because in a call wrapped across multiple lines, **the helper name appears only on the first line** (looking at just the continuation lines makes it look bare).
- **`config` names its lineage from different material.** Because `config` touches the user config and the decision log next to it, its lineage naming works backward from **where the user config lives** (`--root` / `--config`), not from the runtime directory. The `--runtime-dir` form doesn't apply -- `config` takes none of the verb's options, so passing it fails with "takes no arguments." At a layer where the naming can't be determined yet (an option check that runs before the settings location is resolved), the message names **the entry point** instead of writing a "one line to type" with `rein ...`.
- **A `config set` / `unset` message names the scope too** (`--user` / `--project`). The default is the project layer, so a message that defaults silently for a value that actually lives in the user layer produces a copy-pasted line that **runs but changes nothing** -- the same failure mode as dropping the lineage naming. Where the layer is known, the message names it from the value's origin; where it isn't, the message shows both layers explicitly. The canonical rule for this lives in [the settings-layer specification](config.md). `config get` folds the layers together when it reads, so it carries no scope.
- `self-path` counts **a `cd` / `pushd` whose destination is decided by command substitution** (the shape `cd "$(dirname "$0")"`). On a machine where that command returns empty or `.` -- because something placed a same-named command earlier on `PATH` -- the destination falls back to the caller's current directory, and rein then loads and runs a bundled-library path built from there. (Launching it in a directory where such a trap has been planted makes the trap run with that process's privileges -- observed directly.) The safe form is to cut `${BASH_SOURCE[0]}` apart with **shell string operations** (the canonical form is the location resolution in `scripts/lib/rein-common.sh` and `scripts/rein-hook.sh`). Relative-path handling comes in two shapes -- drop it, or prefix it with the current directory -- and neither starts an external command, so neither falls under this gate. Excluded: comment lines, `case` branch pattern lines, and any line declared exempt with `self-path-exempt: <reason>` on the same line.
- `gate-table` catches **the reverse direction from the gate table to the implementation** -- writing a `gate_*` function and forgetting to add it to the table, which means that gate never runs. The table-to-implementation direction is caught at run time by `run_gates`, so together the two directions cover both. Because it cross-checks **name-and-function-name pairs**, this same single pass catches not only a missing registration but also a mismatch between the table's first column and the name the function claims for itself (where the spelling in the result line splits from the spelling `--gate` names). An exception is declared by writing `gate-table-exempt: <reason>` on the `local gate=` line.
- The ten gates from `self-lib` through `gate-table` all catch **the same shape of gap** -- an already-correct mechanism left unapplied in just one spot -- by machine. Every one of their exemption forms is written the same way, **as a reason on the line itself** (`self-lib-exempt:` / `launcher-exec-exempt:` / `run-limit-exempt:` / `home-base-exempt:` / `record-append-exempt:` / `test-side-scope-exempt:` / `stop-order-exempt:` / `flag-value-exempt:`). `section-table` alone judges at the file level, so its exemption, `section-table-exempt: <reason>`, goes anywhere in the file. A separate table would leave no way to tell whether the table or the actual code is stale.
- **`record-append` is the only gate that excludes test-side writers** -- functions whose names start with `st_` / `rein_st_` / `fake_`, or `selftest` itself. The test side only ever touches a temp directory it created itself, so it never falls under the append-discipline for records (the threat model's "outside" is anything a target project could ship). **The prefix never includes a writer verb like `write_`** -- that's a spelling a production writer would naturally use for itself, and including it would exclude a production writer from the scan on name alone (this actually happened, excluding the three functions that write the running heartbeat, the pointer, and the stop marker). A test-side writer instead names itself `st_write_*`, which the `st_` prefix already excludes. **The suffix (`*_selftest`) is never included either** -- a production function like `gate_selftest` naturally uses that spelling, so excluding by suffix would drop a production writer on the name alone. An exact match on the single word `selftest` is enough, since every script's selftest entry point is unified under it. The scan **never reads the inside of a heredoc as a function boundary** (reading a `name() {` / `}` inside the heredoc's body as a boundary would swap in the enclosing function's name for the inner one). **`test-side-scope` closes off the trick of renaming into this exclusion** -- a test-named function can't be called from a production location, so a production writer that took on a test-side name gets caught at its caller (even if every caller in the chain renamed itself too, the top of the chain is always either `main` or the top level, which is production, so some live path always gets caught). **No other gate carries this exclusion** -- test-side lines are excluded from every other gate the same way as everything else, one declared reason per line.
- `stop-order` clears its "the output was already emitted" state every time it passes a record line. This matters when one function has two branches that block a stop -- the normal handover trigger, and re-blocking a stop for a rejected generation -- so that one branch's output can never end up shielding the other branch's record.
- `dist-author` reports `SKIP`, not `PASS`, at a scan root missing even one of the three spots (so a missing spot is never read as "they all match"). It pulls the name from `LICENSE`'s copyright line.
- `scan-source`'s second check uses `git check-ignore`. Copying `ls-files --exclude-standard`'s output into the check side would make it a second implementation looking at the same thing, so it cross-checks through **a different entry point** instead.
- When a prerequisite tool is missing (`shellcheck`, `jq`, or `perl` for the selftest deadline), the gate is never silently skipped -- it fails, with a reason shown.
- **A gate with zero targets reports `SKIP (0 files)`, not `PASS`** (a state where nothing was actually checked is never read as green).
- `bash32` reports `SKIP` when the `bash` on `PATH` is the same binary as `/bin/bash` (since the `selftest` gate already ran on the real 3.2 binary). This avoids running twice, but the skip itself is still shown. In an environment with a newer `bash` earlier on `PATH`, it actually runs both times.
- `bash32` pins **both the outer layer (the runner) and the inner layer** (the `bash <script>` that selftest uses to relaunch the target itself) to the real 3.2 binary. Pinning only the outer layer still lets the inner layer pull whatever `bash` is on the machine's `PATH`, so `PASS` comes out with the outer layer on 3.2 and the inner layer on 5.x (observed). The inner layer's entry point is the environment variable `REIN_SELFTEST_BASH`, **defaulting to `${REIN_SELFTEST_BASH:-${BASH:-bash}}` -- the very `bash` currently running the outer layer** (the value's single canonical holder is `REIN_ST_BASH` in `scripts/lib/rein-selftest-fixtures.sh`). Whether the result line reads `PASS` or `SKIP`, it names both the outer and inner `bash` -- so the display alone is never read as "this ran on 3.2." **Only an internal launch that routes through `$REIN_ST_BASH` can be pinned this way** -- a form that launches the target script directly (via its `#!/usr/bin/env bash` shebang) runs on whatever `bash` is on the machine's `PATH`.
- `selftest` and `bash32` print each script's name plus `START` before launching it, and stream stdout / stderr as they're captured into a regular file. Each run gets a finite deadline -- 600 seconds by default, 3600 seconds at most. An oversized value, an overflow, or exceeding the cap is rejected before launch; exceeding the deadline itself leaves a non-zero exit with the target's name, its output so far, and its exit code.
- selftest's process control is centralized in an internal supervisor that runs on macOS's stock `perl` (`scripts/lib/rein-selftest-supervisor.pl`); the only caller is `check.sh`'s `run_one_selftest`. The supervisor forks a child, has it call `setpgid(0, 0)` to create **a dedicated process group led by itself** and then `exec` the target -- the supervisor itself stays outside that group. Once the deadline passes, it sends TERM to the group (`kill -$pid`), waits 0.5 seconds, then sends KILL. Killing just the leader would leave **descendants that ignore TERM** behind in the group, so it kills the whole group instead. **Any INT / TERM / HUP / QUIT the supervisor itself receives is forwarded verbatim to the same group** -- the child sits in its own process group and never receives the terminal's Ctrl-C directly, so without forwarding, only the caller and the supervisor would die while the target kept running, orphaned (observed: without forwarding, the target and its children were still alive 0.8 seconds after the disconnect; with it, none were). Forwarding is independent of the deadline branch and **only sends** -- it adds no grace period and no KILL, and once the target is reaped its exit code passes through unchanged (`128 + signal number`), never becoming the deadline's `142`. A descendant that ignores the forwarded signal is left alone, and from there the deadline's TERM-then-KILL takes over. To close off the case of killing before the child finishes its own `setpgid`, **the parent sets the same group too** (this fails if the child has already `exec`'d or exited, in which case it's swallowed, since the child has either already set it itself or there's nothing left to kill). However, `run_one_selftest` starts the supervisor with `( ... ) &`, so **on that path INT and QUIT are inherited as `IGNORE` and never reach either the supervisor or the target** (this is the shell rule for asynchronous commands in a non-interactive shell; observed: a `perl` started inside `( ... ) &` reports `%SIG` as `INT=IGNORE QUIT=IGNORE TERM=DEFAULT HUP=DEFAULT`) -- so on this path, only TERM and HUP actually get forwarded.
- The deadline is measured with a monotonic clock, not wall clock (`Time::HiRes`'s `clock_gettime(CLOCK_MONOTONIC)`), so a clock adjustment or a daylight-saving shift never stretches or shrinks it. Waiting is done with a poll every 0.02 seconds via `waitpid(..., WNOHANG)`; **a blocking `waitpid` is never used**, because it can't be interrupted with `SIGALRM` (observed). There are only three branches: once the target is reaped, its exit code passes through (`128 + signal number` if it died from a signal; `125` for a wait result that can't be read either way); a negative return from `waitpid` fails with a reason; anything else continues polling. Only a run killed by the deadline returns `142` instead of the target's own exit code (the same value as `check.sh`'s `SELFTEST_DEADLINE_RC` -- if the two ever disagree, the `proc:deadline` hang fixture fails).
- Reaping only reaches **the processes that stay inside the process group the supervisor created, and their descendants** -- once selftest itself leaves that group via `setpgid` / `setsid`, it's out of reach (the current fixtures are limited to shells and `exec`, and don't do this). **Only two things trigger a kill: exceeding the deadline, and forwarding a caller interruption.** A run that hits neither and finishes within the deadline never sends a single signal, so any descendants the target left behind can simply keep running. What still keeps the runner from waiting on them is that output capture uses a regular file, not a pipe (see the next item). The capped runner for external commands (`rein_run_limited`) uses the same foundation (`fork` -> `setpgid` -> a `WNOHANG` poll) but kills differently; the reason it skips TERM's grace period belongs to [the handover specification](handover.md).
- The command's stdin is pinned to `/dev/null`, so it never sits waiting on input. stdout / stderr are captured by having the process append to a regular file, not a pipe, so that a descendant of the leader that exits while still holding the fd open never leaves the runner waiting indefinitely. The runner creates a temp control directory, follows the output file inside it and displays **only the lines not yet shown**, and reads the supervisor's exit code from a result file in the same directory (there's no cap on how much is read or written). If the output can't be followed, can't be displayed, or the exit code isn't a number, it exits non-zero with a reason and the evidence path shown, **without deleting the temp directory**.

### Getting shellcheck to pass on split files

Splitting the implementation across multiple files under `lib/` surfaces warnings that never appeared as a single file (observed on shellcheck 0.11.0). **Each warning needs a different way of silencing it**, so none of them get a blanket file-wide `disable`.

- **An uppercase global variable draws no warning when it's only referenced** (shellcheck treats it as an environment variable). Reading `$TARGET_CWD` from a different file alone triggers no SC2154. What fails is **the side that assigns it**, with SC2034 ("appears unused") -- the straightforward fix is to move the state's initialization block into the same file as the layer that uses that state.
- **A lowercase variable draws SC2154 just from being referenced.** Reading a caller's check-only variable from a section file always triggers this, so it's silenced with `# shellcheck disable=SC2154` (with a reason comment) at the top of the file.
- Reading an uppercase global in a file that also has a `local` of the same name triggers SC2153 (misspelling); this is silenced with a line-level `disable`.
- **An uppercase global that a shared helper only assigns** (a background job's pid, say) triggers SC2034 on the helper's side, since its readers are scattered across section files. Rather than widening this file-wide, a line-level `disable` **naming the reader's file** goes right above that line.
- **`# shellcheck source-path=SCRIPTDIR` only affects the one command right after it** (it covers the whole file only when placed at the top, before any command). When several `source`s appear in a row, **write it again immediately before each one**. Skipping it produces SC1091 ("Not following") at info level, which under the default severity still exits 1 -- turning the gate red.
- **A `source=` relative path is anchored to that file's own location.** Moving a file means fixing the directive's path too -- the runtime path derived from `$SCRIPTS_DIR` is a separate thing from the directive.

### Running a single gate

A gate can be run alone by name (the name is the exact text from the table above, matching the text in its result line).

```sh
scripts/check.sh --gate docs-links
```

- The output takes the same shape as a full run, but shows only the result line and summary line for the gate that ran. The exit code reflects that gate alone.
- **A missing gate name, or a name not in the table, fails** (exit code 2, with the selectable names shown). Silently running zero gates would look identical to every spelling being wrong and passing.
- `--gate` takes exactly one gate name; giving it two or more also fails with exit code 2 (a mistaken argument list is never silently accepted).
- **Never copy what a gate checks (the gate table itself, say) somewhere else and cross-check it by hand** -- run that gate through this entry point instead. A copied list never tracks the original, and becomes a second implementation looking at the same thing.

### Don't restrict who runs the gates

**Anyone may run any gate** (the table carries no "who may run this" column, and no entry point takes an option for declaring intent).

- `selftest` and `bash32` run each script's bare `--selftest`, which reaches the "Sections that go through process control" path below. There, the TERM / KILL the supervisor sends on a deadline overrun **only ever reaches the dedicated process group created by `setpgid(0, 0)`** -- what gets killed is only the process that test itself started, regardless of who's sitting at the machine.
- The default deadline is 600 seconds. The heaviest selftest (`bin/rein`'s) takes around 200 seconds by measurement, and gets close to 300 on a busy machine (when the default was 300 seconds, 3 out of 5 runs failed here). **The deadline is a guardrail, not a target** -- it doesn't get lowered just because the actual time shrinks. What it kills is always confined to that same dedicated process group.

## selftest conventions

**Every shell script outside `lib/` (currently everything directly under `scripts/` and under `bin/`) is treated as an executable script, and must have both the execute bit and `--selftest`** (`check.sh` fails if either is missing). Everything under `scripts/lib/` is treated as a shared library and needs neither -- even when its own check logic lives there, the entry-point executable script is still the one called with `--selftest`.

| Item | Convention |
| --- | --- |
| Launch | The first argument is `--selftest` |
| Selecting sections | A script with sections can run just some of them with `--selftest <section-name> [...]` (all of them if omitted); `--selftest --list` lists the section names |
| Failure line | `  FAIL <name>: <detail>` |
| Final line | `<script name>: selftest N pass / M fail` |
| Exit code | 0 if everything passed; non-zero if even one failed |
| Target | Fixtures in a temp directory only |

- `check.sh` also validates the final line's format, that the script names itself correctly, that `N > 0`, and that `M = 0` -- so a no-op that ignores its arguments and just `exit 0`s never passes.
- What counts is decided by **content, not extension** (`*.sh`, plus any file whose shebang names a shell). Deciding by extension would put the extension-less command binary (`bin/rein`) outside every gate's reach. A shebang naming something other than a shell is never in scope.
- Whether the execute bit is set doesn't decide it either (otherwise a forgotten `chmod +x` would never be caught as a violation -- the file would just go silently unchecked).
- Checks **never touch real config or real state, and never trigger a GUI notification.** `REIN_NOTIFY_SILENT=1` suppresses the GUI notification (a line to stderr still remains, so a check can still observe that a notification would have fired).
- **Building the isolation environment always goes through the single `rein_st_isolation_env` (`scripts/lib/rein-selftest-fixtures.sh`) -- entry points never write out their own `env` lists.** This function works by first dropping every single variable starting with `REIN_` currently in the environment, then rebuilding just the check's own entries afterward (user config, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `HOME`, never-touch roots) -- `env` lets the later entry win. An entry point that needs to add a value of its own appends it **after** the returned `REIN_ST_ENV_ARGS`.
  - **The point is to never keep a list of what to drop.** A form that enumerated "config's known keys, plus the isolation entries, plus the managed marker" actually let a reader belonging to none of those lists (`REIN_MANAGED_SETTINGS_POLICY`) leak through. Adding a new `REIN_*` reader never requires updating the isolation side to keep up.
  - **Never lay out `bin/rein --root <dir>` or `REIN_CONFIG_FILE` / `REIN_RUNTIME_DIR` by hand.** This is exactly how the incident happened -- a child ran with the surrounding `REIN_MANAGED_*` still set, and it wrote the fire log and the `hooks/` drop-in into real state.
- **A child that resolves its location to somewhere under a never-touch root fails loud.** Before dropping the environment, the parent records "the roots that must never be touched" -- the runtime directory the managed marker names, that directory's parent (the root of the state area), the records location, and the real state root resolved from XDG -- and passes them to the child via `REIN_SELFTEST_NEVER_ROOTS`. The child runs this through `rein_selftest_never_root_hit` (`scripts/lib/rein-common.sh`) **right after resolving its location, before writing a single byte**. The gate is armed by **whether this one env var is non-empty**, nothing else -- it doesn't look at a separate marker like `REIN_HOOK_SELFTEST` (in production it's empty, so one string check lets the run through).
  - The gate is present in **every executable script that resolves a location and writes to it.** The entry points and where the gate sits are below, and **no executable script is left without one.**

    | Entry point | Where the gate sits | Location it checks |
    | --- | --- | --- |
    | `scripts/rein-hook.sh` | `hook_prepare` | runtime directory, records |
    | `bin/rein` | `prepare_runtime` in `scripts/lib/cli/base.sh` (every writing verb goes through it) | runtime directory, records |
    | `scripts/rein-watcher.sh` | records branch: `resolve_target_cwd`; runtime-data branch: `resolve_paths` | records / runtime directory, records |
    | `scripts/rein-request.sh` | end of `load_config` | runtime directory, handoff document |
    | `scripts/rein-seat.sh` | right after `run_seat` resolves the records location | runtime directory, records |
    | `scripts/rein-statusline.sh` | end of `statusline_resolve_dir` | the usage location (`usage_state_dir`) |

  - **The check is never added per write site** (one forgotten site would just become a hole). It's split into multiple stages only for **an entry point whose location resolution itself happens in multiple stages**; the deciding factor is whether a failure path upstream of the gate writes to disk. `rein-watcher.sh` needs two spots because, before it even reaches the records branch, `startup_reject -> wlog` already creates `watcher.log`. The other five are covered by one spot each, because their upstream failure paths only go to stderr and a GUI notification.
  - **Which location each check watches follows what that entry point actually writes** (never mechanically pairing the runtime directory with records). `rein-request.sh` passes the handoff document rather than records because requesting a handover never writes a byte to records (`watcher_start_hint` only reads them) -- instead, right before publishing, it `touch`es the handoff document. Since the default `handoff_path` sits right next to the records, this still catches a break in isolation on the records side too. `rein-statusline.sh` uses neither the runtime directory nor records; it writes only to `usage_state_dir` (it looks read-mostly, but it's the sole writer of `<usage_state_dir>/<session_id>.json`).
  - **The gate is never placed inside the shared resolvers** (`rein_resolve_runtime_dir` / `rein_records_dir`). The hook's managed-marker path never goes through the resolver at all -- it uses the env value directly -- so a gate placed there would miss the branch that actually matters.
  - **The failure message goes straight to plain stderr, never through that entry point's own logging mechanism** (routing it through `rein-watcher.sh`'s `wlog` or `rein-seat.sh`'s `startup_reject` would have the failure itself write a file under the never-touch root or trigger a GUI notification).
  - **Adding a new entry point means adding its gate too** (the deciding question is always whether this entry point resolves a location and writes to it). Layered on top of the gate, two more checks remain: (a) `ST_NEVER_PATHS`, which checks on every run whether a location that should never exist has appeared, and (b) `scripts/rein-hook.sh`'s selftest, which fingerprints real state on every run.
  - **The gate only checks under the roots `rein_st_never_roots` assembles**, so every root a write could fall under has to be gathered into this one function. The three families it lists: the managed marker's real family (runtime directory, its parent, records), the real state root resolved from XDG, and the usage-tracking default (`${HOME}/.claude/state/context-usage`). The third one's material is `HOME`, which falls under neither of the first two, so dropping it would leave `rein-statusline.sh`'s gate watching none of its actual leak targets. What ends up in the list is pinned directly to the values `scripts/rein-hook.sh`'s selftest builds (checking only "does it trip / does it not" would leave both green even if a whole family were dropped).
- A check that ends up launching a real script always goes through this isolation, the gate, and notification suppression before launching it.
- A check never touches the real repository's files or real state.
- A check covers **both sides** of a judgment -- that what should pass does pass, and that what should fail does fail.
- **Never use elapsed wall-clock time to decide pass/fail.** Judging a branch by whether it took less or more than N seconds makes the exact same code go green or red depending on how busy the machine is (observed: a run that only failed when running alongside other selftests, crossing a `5-second cap` boundary -- green and red both came out of the same working tree). Instead, measure at an **observation point**: a line in the handover log, a state file's appearance and its mtime advancing, the exit code of an external cutoff (`128 + SIGALRM` = 142), a call count a shim tallied, or a cycle a shim halted. When the duration itself is what's under test and can't be swapped for an observation point (the length of a grace period is set by a config value, say), **move it away from the boundary**: leave an order of magnitude between the config value and the measured duration, and write the reason right there. **A lower bound ("waited at least N seconds") can stay, since load only ever stretches it; an upper bound ("finished in under N seconds") gets moved to an observation point, since load is what crosses it.**
- A waiting entry point (`st_wait_for_*`, an observer) is shaped as "wait until it appears, exit the instant it does," with its cap set well clear of the observation's actual duration. A fixed `sleep`-then-read-once form fails on any run where load delays the observation.
- **Never observe a fast-cycling target by "slowing it down."** Widening the interval to get the observation done ahead of time still lets a busy machine delay the observation past the next cycle. Instead, a `sleep` shim at the front of `PATH` **stops only that target's own cycle sleep** (distinguished by the caller's command line), confirms the stop with a marker, then measures.
- **A section name is `<layer>:<name>`.** There are two layers: `proc` (starts a watcher, seat, or fake-CLI child process -- heavy) and `pure` (argument parsing, settings layers, pure functions only -- light). `--selftest --list` shows on the spot which sections are cheap to run.
- **Every section must be able to run on its own** (a foundation shared by several sections gets built at the selftest entry point or in a shared helper, never inside whichever section runs first). Building on top of what a previous section left behind fails only when that one section is run alone.
- **When adding a case to an existing section, never name the new function `st_section_*`.** That prefix isn't called unless it's registered in the section table (`rein_st_section_table`), and **the check that catches a missing registration only runs in one direction** -- table entries with no matching implementation. The reverse (a name shaped like `st_section_*` that never made it into the table, and so is never called) is caught by nothing. So if the goal is to avoid adding a new section, give the function **an ordinary name that an existing section's function calls**.
- **After adding a case, confirm the pass count actually went up** (and after splitting a section, check the reverse too -- mutate the code so **one section never gets called**, and confirm the count drops, before calling it done; a matching total alone can miss a broken call wire). selftest runs under `set -uo pipefail` (no `errexit`), so **calling an undefined helper name just prints one `command not found` line to stderr** -- neither pass nor fail increments, and the assertion silently disappears. Splitting or moving a section file and shifting the `source` order can thin the count the same way. The names actually available are whatever's listed in the `helpers.sh` and shared fixtures (`scripts/lib/rein-selftest-fixtures.sh`) that entry point sources -- **the visible set differs per entry point**, so never carry a name over from what was visible at a different one.
- **A test may pin the exact text of output only when that text is a discriminator or a contract** -- a failure's stated reason (an exit code alone can't distinguish one rejection reason from another), a line the user reads in the CLI, a handover-log or notification detail, or text duplicated deliberately with kickoff or a skill. Everything else -- column alignment, whitespace, how a count looks -- gets verified by parsing its properties instead (for example, "descriptions in usage text start at one column within a section" is checked by parsing the output, so it never fails just because wording or a verb count changed).

```sh
scripts/check.sh --selftest
```

### Splitting a large executable script

The numbers below were measured when `bin/rein` (5032 lines before the split) was split out into `scripts/lib/cli/`. **bash parses the whole script at startup**, so pulling a huge, rarely used block (selftest) out into a separate file and `source`ing it conditionally speeds up startup (measured 53.1 -> 47.6 ms per run) -- on a path that runs on every tool call, like hooks, that difference is felt directly as latency. `scripts/rein-watcher.sh` is split the same way, into `scripts/lib/watcher/selftest/`.

Steps for splitting a large selftest function into sections (bash 3.2):

1. Create `st_section_<name>()` for each section and move its body over as-is, indentation included.
2. **Hoist every `local` declaration found mid-function up to the top of the caller.** A declaration inside a section function *isn't visible to the next section* (dynamic scope reaches callees, but not siblings). Before deciding a hoist is safe, confirm mechanically that the name never appears above its declaration line.
3. Shape the caller as: the `local` group, then setup, then calling the sections in order, then cleanup and the summary. `trap ... EXIT` and an early `return` stay in the caller (a `return` inside a section just returns from that section).
4. Registering section names and confirming the count follow the selftest conventions above (a name shaped `st_section_*` is never called unless registered in the section table; check the count moving in both directions).

Pitfalls when splitting:

- **A check that pins a contract by `grep`ing the implementation file** (cross-checking a shorthand table against a `case` statement's list, say) can lose scan coverage from a split. When widening what it scans, **always add `grep -h`** -- passing multiple files prefixes each match with a filename, which zeroes out a downstream filter and leaves **the check running on nothing, still green**.
- Put the selftest implementation somewhere the implementation-file glob doesn't reach (one directory down, like `lib/cli/selftest/`). Sharing the same glob would get a fake-CLI `case` statement inside the check read as one of the implementation's own shorthands.
- A split changes no external behavior, so **the same argument list can be run before and after and its output and exit code diffed** (writing `git show HEAD:bin/rein` out into a separate directory builds the pre-split side). Normalize any value that varies from run to run -- a temp-directory path, a key, a timestamp, seconds remaining -- before comparing.
- **Whether every line actually moved can be checked mechanically, as a multiset of lines** -- normalize both the relevant range from `git show HEAD:<file>` and the new set of files (strip leading/trailing whitespace, drop blank lines, `sort`), then `comm` them. The only lines allowed to disappear are **the shellcheck `source=` relative paths rewritten because of the move**; the only lines allowed to appear are the generated headers and the definitions, calls, and closing braces of `st_section_*`.
- **Proving "this is only `source`d when `--selftest` runs" means temporarily `mv`ing the section directory and measuring the result**: `--help`, an unknown argument, and one real scan all still pass with the same exit code as before the split, while `--selftest` alone fails with 127. Reading the code and stopping at "it's inside the conditional" isn't enough.

### Sections that go through process control

`scripts/check.sh`, `scripts/check.sh --selftest` with no arguments, and `scripts/rein-seat.sh --selftest` with no arguments all go through paths that can reach process termination. The first two send TERM / KILL to an intentional hang's dedicated process group; the last one sends a signal as part of checking interrupt-time cleanup. **This still doesn't restrict who runs them** (see "Don't restrict who runs the gates" above). Since these are heavy, use the targeted sections below to run something cheaper.

```sh
scripts/check.sh --selftest pure:safe
scripts/rein-seat.sh --selftest proc:safe
```

**There is one supervisor (`check.sh`'s `run_one_selftest`), and the two gates that launch `--selftest` both go through it** (`selftest` and `bash32` -- both run against the same supervisor, once on the `bash` from `PATH` and once on the real bash 3.2 binary). There's no separate backend per section; even `pure:safe` goes through the production supervisor. What this setup guarantees is **the scope of what gets killed**, not that nothing gets killed -- the supervisor's kill scope, and the only two things that trigger a kill at all, are canonical under "Running the gates" above (not repeated here).

What `pure:safe` covers is **every path that never reaches process termination (TERM / KILL)** -- every gate's fixtures, plus, for the supervisor: display order (`START` -> stdout -> stderr -> exit code), the streaming display shown before selftest finishes, cleanup failure of the control temp directory, rejecting an out-of-range deadline value, and displaying the deadline branch. The one deadline-branch case is measured with **a fixture that returns `142` without actually waiting** (the combination of a real hang and a real process group is measured by `proc:deadline`). A safe fixture that does wait carries its own finite cap (`CHECK_ST_STREAM_MAX_POLLS` polls) and finishes on its own well ahead of the wrapper's deadline. **Whether it actually got killed is something the fixture checks for itself** -- it traps TERM / INT / HUP, prints a `FAIL` line, and exits, so if the supervisor ever did kill something in this section, the check itself would go red. `proc:safe` (`rein-seat.sh`) starts short-lived child processes, but only uses cooperative shutdown via a stop-request file and a natural exit cap -- it never invokes process termination. `scripts/check.sh --selftest proc:deadline` is the section that actually measures an intentional hang, checking the deadline-overrun display, **that a descendant ignoring TERM disappears along with its whole group**, and that no fixture temp state is left behind.

The runner's control directory and the seat selftest's temp root both fold their own deletion result into the final status; on failure, the reason and the evidence path are shown and left in place. `proc:safe` checks the negative side -- that even a green check body still exits non-zero on a cleanup failure -- and that the evidence is actually left behind, without going through process control.

## Terminology (use this word for this concept)

**This is the terminology contract**: use only terms that trace back to what they name in the implementation. A metaphor gets reinterpreted differently case by case, and the reader loses track of which code path is actually meant. The concepts below always use the word given; a concept not listed here may be phrased freely.

| Concept (what it names in the implementation) | Term to use |
| --- | --- |
| The session that places a handover-request marker to hand off to a successor, and that act itself | the requesting session / to request a handover |
| The event and mechanism that moves work from one session to its successor, and the files it reads and writes (`handover-request.json`, `handover.log`) | handover |
| The document a session writes for its successor, named by `handoff_path` | handoff document |
| The seat itself -- where the user's own terminal is connected via `claude attach` | seat |
| The loop that watches the current pointer and keeps re-attaching via `claude attach` (`scripts/rein-seat.sh`) | attach loop |
| The act of connecting to that seat | attach |
| The active session currently doing the work on the target project | primary session |
| A `watcher.lock/` determined to have no living owner (its pid is gone, or the pid is alive but belongs to a different process) | stale lock |
| The stage of waiting for the predecessor session to drop out of the `claude agents --json` enumeration | exit confirmation |
| Ending the predecessor session from outside, via `claude stop` | external stop |
| A check silently becoming a no-op and doing nothing | silently defeated |

- A rejection that names a different rule than the actual cause (say, because a required tool was missing) gets no coined term -- describe the behavior directly instead (for example: "rejects with the lock-contention reason, not the JSON-parse reason").

## Versioning

**The single canonical source for the version is `version` in the plugin manifest** (`.claude-plugin/plugin.json`). Everything else is derived from it: `rein --version`'s first line, `claude plugin list`'s display, the location of the receiving side's plugin cache (`~/.claude/plugins/cache/claude-rein/rein/<version>/`), the `<version>` in the distribution archive name below, and every selftest expectation -- **no copy of the literal text lives anywhere else** (keeping even one copy makes the act of bumping the version itself turn the check red -- this actually happened).

| Bump | When |
| --- | --- |
| patch (`1.0.x`) | A fix with no externally visible behavior change (implementation cleanup, checks, docs) |
| minor (`1.x.0`) | A backward-compatible addition (a new verb, option, or settings key; no default value changes) |
| major (`x.0.0`) | Bumping a contract schema version; requiring the receiving side to reinstall or migrate by hand; or a default-value change that alters an existing lineage's behavior |

- **A contract schema version (`rein.handover-request.v1` / `rein.current.v1` / `rein.handover-log.v1`) moves independently of the plugin's own version.** A schema is a promise to whatever reads the file it names, so bumping it means a newer version will refuse the runtime data an older version wrote -- **a schema bump is always major** (`rein --version` prints the schema version as its second line, so the receiving side can judge from that one line alone). Bumping only the plugin version while leaving the schema alone is a patch or minor.
- **Per the official spec, setting `version` pins the plugin to that version string** ("Setting this pins the plugin to that version string, so users only receive updates when you bump it"; when both plugin.json and the marketplace set it, plugin.json wins). Under the current distribution method -- a local directory registered as the marketplace source -- bundled files are read from the source itself, so a `git pull` alone delivers an update. **But moving to a git- or URL-based source means the receiving side gets no update at all until the version is bumped.**
- After bumping the version, **hand out the archive name and `shasum` value for the new version too** (the receiving side has no way to confirm identity other than the name and the SHA-256).

## Distribution

The deliverable is a single checkout of this repository (the receiving side's steps are step 1 of "Quick start" in [the user-facing guide](../../README.md)). When handing it over as an archive, **build it from a snapshot of only the files git tracks, and include a SHA-256.**

```sh
git archive --format=tar --prefix=claude-rein/ HEAD -o claude-rein-<version>.tar
shasum -a 256 claude-rein-<version>.tar
```

- **Never just compress the working tree as-is** -- untracked files like `.rein/` (where lineage records, including the handoff document, live) would get mixed in. When this repository runs rein on itself, what ends up in there is **the handoff document describing work on a different project**. `.rein/` is listed in `.gitignore` to close off this same accident structurally, but an ignore rule doesn't guarantee "nothing gets mixed in" (other untracked files can still appear), so the archive-building step closes it off too.
- **`--prefix=claude-rein/` wraps the extracted contents in a single directory.** Omitting it means `tar -xf` scatters the top-level items (nine of them: `.claude-plugin` / `.gitignore` / `LICENSE` / `README.md` / `bin` / `docs` / `hooks` / `scripts` / `skills`) straight into the receiving side's working directory, silently overwriting any file with the same name. The receiving side's step (step 1 of the README's "Quick start") is to `cd` into the `claude-rein/` the extraction produces, so without the wrapping directory, that one step doesn't work either.
- **The SHA-256 is the receiving side's only way to confirm they got the same thing** (there's no signed tag, no distribution channel). `shasum` is already among the tools the receiving side needs anyway, so they can verify it without installing anything extra.
- **No separate step re-verifies the extracted contents' file list or permissions.** `git archive` emits only tracked files, with the mode git already has recorded. If an extracted copy has lost its execute bit, `rein doctor` returns non-zero with "the hooks execution path does not resolve," and `rein init` always runs doctor at the end, so the receiving side hits that check the moment they install.
