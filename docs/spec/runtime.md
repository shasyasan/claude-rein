# Locations and Locks Specification

How lineages are separated, what goes where, each file's writer and reader, locks and heartbeats, how a stop request is handed off, and the settings a background session is launched with.

## Unit of management

The unit of management is one lineage per (target project (cwd), root) pair.

- At the default root, there's one lineage per cwd. Project memory, the handoff document, and the task log are all tied to the cwd, so handover state is split along that same unit.
- **Pointing `--root` at a different root lets a second lineage run alongside the first for the same cwd** (running separate backend and frontend lineages against the same repository, say).
- When that happens, the lineage's records move to the root's side too -- sharing `<cwd>/.rein/` would let the two lineages overwrite each other's current pointer, with no way to later recover which lineage a given primary session belonged to.
- **The key** is `<basename of cwd>-<first 12 hex digits of the SHA-256 of cwd>`.

## Locations (split in two, by who owns the lifetime)

Lineage records (that working tree's history) live on **the project side**; runtime data (what belongs to a process currently running on that machine) lives on **the machine side**.

| Kind | Location (default root) | Lineage under `--root <dir>` | Where it's overridden |
| --- | --- | --- | --- |
| Lineage records | `<cwd>/.rein/` | `<dir>/records/rein/<key>/` | `--root` (short form `-R`), `REIN_RECORDS_ROOT` |
| Runtime data | `${XDG_STATE_HOME:-~/.local/state}/rein/<key>/` | `<dir>/state/rein/<key>/` | `--runtime-dir` (short form `-D`), config's `runtime_dir`, `REIN_RUNTIME_DIR` |
| Settings (user) | `${XDG_CONFIG_HOME:-~/.config}/rein/config` | `<dir>/config/rein/config` | `--config` (short form `-F`), `REIN_CONFIG_FILE` |
| Settings (project) | `<cwd>/.rein/config` | `<cwd>/.rein/config` (not split by root) | follows `--cwd` |
| Project-settings allowlist | `${XDG_CONFIG_HOME:-~/.config}/rein/allowed-project-configs` | `<dir>/config/rein/allowed-project-configs` | follows the user config's location |

- Lineage records consist of `current.json`, `handover.log`, `seat.log`, `watcher.log`, `hooks.log`, and **the handoff document, `handoff.md`** (this is its default location; `handoff_path` can move it).
- Runtime data consists of the handover-request marker `handover-request.json`; `watcher.lock/`, `op.lock/`, `seat.lock/`, `handover.lock/`; `watcher.heartbeat`, `watcher.stop`, `seat.stop`, `snooze`, `handover-ready`, `handover-cancel`; `hooks/`, `children/`, `managed-settings.*`; `processing/`, `processed/`, `rejected/`, `cancelled/`; `owner`, `token`; and the temp name `*.rein-tmp.*` used for atomic writes.
  - **This one line is the human-readable canonical list of runtime-data names**; the canonical source on the implementation side is a set in the shared library (the known runtime-data names). The selftest cross-checks both directions, so adding a name means fixing both this line and the implementation's set (fixing only one fails the check). The cross-check only looks at what's inside the backticks on this line; a trailing `/` is dropped as decoration marking a directory before comparing.
  - The temp names left behind by a failed lock acquire or release (carrying a `.claim.` / `.release.` suffix hung off the lock's published name) count as rein's runtime data too, and get cleaned up under the same discipline. They're derivable mechanically from the published name, so they're not listed above.
  - An atomic write's temp file (before it replaces `<destination>`) always takes the fixed shape `<destination>.rein-tmp.<random>`, and is **listed above as a glob**. Unlike a lock's temp name, its destination isn't fixed to just one thing -- it can appear next to a handover request, a stop marker, or a snooze -- so it can't be derived from a single published name. Giving it a fixed shape lets cleanup tell "something rein made" apart from "something else that wandered into this location" by name alone; without it, a leftover temp file would always fail `rmdir`, and that lineage could never shut down until someone removed it by hand.
- Project config isn't split by root because it's **that working tree's own settings**, not something a lineage owns (two lineages read the same project settings). But **the permission to let that content take effect** is the user's own call, so it's kept next to the user config -- meaning it does split by root (see "Allowing project config" in [the config specification](config.md)).
- When `.rein/` is created, a `.gitignore` containing only `*` is placed there (rein's lineage records aren't a deliverable of the target project; an existing file or symlink is never touched). **There's exactly one path that can create the records location** -- the shared library's `rein_ensure_records_dir` -- and the handover log, seat records, watcher log, and hooks records all go through it, so whichever writer creates that location first still gets the `.gitignore` placed (creating it with a plain `mkdir -p` would leave the resulting `.rein/` showing up as an untracked file in the user's working tree).
- **On a lineage whose records location is a symlink, writing a record returns 1 with a reason on stderr** -- records are never written out to wherever that link points, which could be outside the project. The same rigor the location-resolving entry point already applies gets applied to the side that prepares the location too: `mkdir -p` follows a symlink and succeeds, so this is checked before creating the final path segment.
- **Every caller of the resolver checks whether it resolved, and stops the command when it didn't** -- the resolver returns 1 with nothing on stdout, so a caller that takes it through `$( )` cannot tell a rejection apart from success with an empty result, and every path built from it collapses to the filesystem root (`/current.json`, `/handover.log`). A caller that stopped there instead reports the resolver's own reason, so a lineage whose `.rein` is a symlink fails the verb it was typed into rather than reading back as "no primary session" and exiting 0. Callers that need the reason resolve **outside `$( )`** and read the value back from the variable the resolver sets.
- **`rein doctor` is the one exception**, because reporting this state is its job: it keeps going with the reason carried in a variable and prints one FAIL line naming it. Since a diagnostic that can't run on a broken installation is no diagnostic, the shared preparation step takes an explicit opt-in for this rather than failing every caller uniformly; every path in doctor that would use the records location already skips an empty one.
- **A lineage under `--root` never gets a `.gitignore` placed at its records location** (writing the `*`-only `.gitignore` is limited to `.rein/` specifically -- it's identified by name). Putting a root under git's control would make the handoff document show up as tracked content in that working tree, so a root either stays outside version control, or `handoff_path` names its location explicitly.
- Runtime data is never placed under the target project because "`tmp/` is outside version control" is **the user's own convention** and this module has no knowledge of it, and because runtime data belongs to "the current process on this machine," not the project.
  - **Hooks require it, and refuse a managed marker whose runtime directory is the lineage cwd or sits under it** (fail-loud, before anything is read or written -- see "A clone can supply the marker env" in [the hooks specification](hooks.md)). A directory inside the working tree is one **the tree itself can be carrying**, `owner` and `token` and all, and those two files are the whole of what otherwise separates a lineage rein provisioned from one a clone shipped. The refusal is on the hook side only: `--runtime-dir`, config's `runtime_dir`, `REIN_RUNTIME_DIR`, and `--root` still accept such a value, so a lineage deliberately placed there stands up and then fails loud on its first hook call.
- It isn't put under `${TMPDIR}` either, because there's no guarantee that the marker's writer (under the session) and the watcher (under a terminal or under nohup) resolve to the same place, and a mismatch there would stop a handover silently.
- kickoff and the handover-request command **always carry every path as absolute** (no branch exists for resolving a relative path under isolation).

### The runtime directory's owner (`owner`)

**The runtime directory holds `owner` (the target cwd, one line), and refuses to start if the owner doesn't match the target cwd** (a mixed-up lineage never proceeds silently).

- Orphan detection is done by checking whether `owner`'s cwd still exists (there's no cross-lineage registry).
- **A runtime directory with no `owner` counts as orphaned too** -- with no way to trace an owner, nobody can determine whether that lineage is still alive, so it's treated the same as "the owner doesn't exist" (`rein prune`'s dry run distinguishes the reason when it displays this).
- **More than one side can prepare the location** -- a lineage can be stood up by the watcher, the attach loop, the handover-request writer, `rein init` / `rein up` / `rein snooze`, or hooks. Writers still don't collide because creating `owner` is a noclobber race, and **the loser still runs whatever got placed there through the same verification before proceeding** -- so a second writer never overwrites it.
- **Every entry point verifies this file before it reads or writes the location** (hooks included), so a lineage that names its location explicitly can never read or write another cwd's markers and latches. What makes hooks act at all is a separate thing -- the managed marker env (see "A window rein didn't launch gets no action from hooks" in [the hooks specification](hooks.md)).

### The lineage token (`token`)

**The runtime directory also holds `token`: 64 hex characters on one line, at `0600`, drawn from 32 bytes of `/dev/urandom`.** It is the one piece of a lineage's identity that **cannot be reproduced from outside it**, and hooks require the managed marker to carry it (see "A clone can supply the marker env" in [the hooks specification](hooks.md)).

- **Why a second file, when `owner` already says which lineage this is**: `owner`'s content is the cwd, which the marker states anyway, so anyone who can write a directory can write a matching `owner` beside it. `token` says something different -- that whoever produced the marker could **read inside this runtime directory**.
- **Written by the same side that claims the owner** (the watcher, the attach loop, the handover-request writer, `rein init` / `rein up` / `rein snooze`, hooks) -- one shared function provisions the location, so a lineage stood up by any of them is complete.
- **Drawn once per lineage, and kept for as long as the runtime directory exists.** A lineage's first session and every successor after it are handed the same value: the handover launch **reads** this file and never draws a new one. A value that moved per launch would leave every generation after the first carrying a marker its own hooks reject.
- **`rein_nonce` is deliberately not reused for this.** That value is the pid concatenated with `$RANDOM` -- a collision avoider for filenames, not a secret.
- **Reading it is strict**: a symlink, a non-regular file, more than one line, or anything but exactly 64 lowercase hex characters is refused rather than compared (an empty file must never become a token that an empty marker field matches).
- **Absent, empty, and mismatched are one outcome on the hook side: fail-loud.** There is no "neither side has one, so proceed" path -- that would hand the bypass back to any marker naming a runtime directory with no token.
- **A lineage claimed before this file existed simply has no token**, and its sessions' hooks fail loud until one is placed. `rein up` (and `rein init`) place one on the next run, and `rein doctor` reports the state with the command to run.
- **The value never appears in a reason string.** Failures name the file's location only -- a reason reaches stderr inside the session and the hook health record, and the side being refused is the last one that should be told the value.
- **What this does not defend**: anyone who can run code as this user can read the file, and always could -- that is inside the trust boundary. The line the token draws is canonical under "Threat model" in [the architecture](architecture.md).

## Cross-lineage cleanup (`prune`'s orphans) closes its target by construction

Because this is an irreversible deletion, **the scan's own range is built into the constraint.** Per-kind candidacy rules are in [the per-verb internal conventions](cli.md).

- The scan only runs on **lineages that never named a location explicitly** (the default XDG state area). For a lineage moved via `--runtime-dir` or config's `runtime_dir`, the scan root would be that value's parent, which isn't necessarily rein's own state area -- so **the cross-lineage scan doesn't run at all** there (one reason line is shown in the dry run).
- Only children matching **the key's shape** (`<basename of cwd>-<12 digits>`) are scanned.
- Whether something looks like rein's own runtime data is decided by whether `owner`, `watcher.heartbeat`, or `watcher.lock/` exist. Generic names alone (`processing` / `processed` / `rejected`) are never treated as identifying it as rein's.
- **Lineage records don't count toward this bar**, since they aren't runtime data -- a runtime directory where they still exist gets treated as "a lineage that never moved its location," **excluded from candidacy, with a message about moving it** (prune never goes and deletes a state the watcher's own startup refusal is protecting). This bar checks exactly two things, `current.json` and `handover.log` -- the two that could exist in an old-layout runtime directory. `seat.log` is a record added later and could never be there; checking for something that can't exist would leave the reader unable to follow the reasoning.
- **The lock side is checked only after orphan status is already decided** -- the same judgment is run against both the watcher lock and the seat lock, and **candidacy is dropped** for a lineage whose owner is alive (the watcher is running, or the user's own terminal has a seat there) and for one whose lock's owner can't be confirmed (`pid` unreadable, or not a number).
- Both are checked because a lineage can have the user's own terminal sitting at its seat even with the watcher down (the discipline of never seizing an unconfirmable lock is upheld in cleanup too). The reason a candidate was excluded is shown as one line in the dry run.
- `-f, --force` **re-checks every precondition right before deleting each candidate** (a watcher can start, or an owner can be placed, in the window between scanning and applying). Deletion works by removing each known runtime-data name individually, then `rmdir`-ing what's left; if something rein doesn't recognize is still there, it's left undeleted, surfacing the problem instead of hiding it.
- **The window between re-verifying and finishing the delete is closed by the target lineage's own operation lock.** `rein up` takes that same lock before starting the watcher at that location, so the two are serialized against each other (a lock scoped to one's own lineage can't serialize against a different lineage starting up -- a lock is scoped per location).
- A lineage whose lock can't be taken (another rein instance is operating on it, or its lock's owner can't be confirmed) is never deleted. Only a lock with no living owner is retaken, under the same discipline as `up` / `down`.
- Calling `scripts/rein-watcher.sh` directly skips this serialization, since that path never takes the operation lock (use `rein up` instead if starting a watcher might overlap with cleanup).

## Lineage records (files on the project side)

**Five files live on the project side, and each has exactly one writer** (no file is ever written by two parties).

| Path | Role | Writer | Reader |
| --- | --- | --- | --- |
| `<cwd>/.rein/current.json` | The current pointer (which session to attach to right now) | watcher **only** | attach loop, the user |
| `<cwd>/.rein/handover.log` | Handover log (JSON Lines, append-only, never truncated) | watcher **only** | the user, audit |
| `<cwd>/.rein/seat.log` | Seat records (JSON Lines, append-only, never truncated) | attach loop **only** -- the loop itself and the stall watchdog it forks, which never write at the same time (see below) | the user, audit, `rein status` |
| `<cwd>/.rein/watcher.log` | The watcher's own operational log | watcher **only** | the user |
| `<cwd>/.rein/hooks.log` | Record of hooks either blocking a stop or letting it through unimpeded (JSON Lines, append-only) | hooks **only** | the user, audit |

- The watcher log records startup, rejections, stage failures, settings reloads, and the reason for exiting.
- **`watcher.log` is the only one with a size cap** (`watcher_log_max_bytes`, default 1 MiB) -- once it's exceeded, one generation is rotated out to `watcher.log.1` right before the next write.
- The handover log is never rotated, because it's the canonical audit trail for handovers -- rotating it would introduce a separate question of "how many generations of audit history are kept," and at a measured 2.5KB per 10 lines, a cap isn't needed. `seat.log` is left unrotated for the same reason.
- **`seat.log` is kept separate from the handover log because their writers differ.** The handover log's writer is contractually the watcher and nothing else, so if seat wrote to the same file, mixed-in lines would leave no way to later recover which mechanism a given line came from. Its column convention matches the handover log's (`schema`, `ts`, `event`, `detail`, `generation`, and the two session columns) -- but since a seat line is never a transition, it puts the subject session in `successor_session_id` and always sets `predecessor_session_id` to `null`.
- **A seat never steps down just because it couldn't write a record** (a record is an observation, and never takes priority over keeping the user's own seat). A failed write leaves one line on stderr.
- **The two writers never overlap.** The attach loop forks the stall watchdog and then blocks in the foreground on `claude attach`; it writes no record of its own until the watchdog has been reaped after attach returns. So "one writer" stays true of the file even though the writer is a parent and a child rather than a single process.
- What gets recorded: taking a seat (`seated`, written once right after the seat lock is claimed and before the first attach); starting an attach (`attach_started`, written **before** entering `claude attach`; because nothing returns for as long as a seat stays attached, writing it only after return would leave the record empty for the whole time someone was sitting there, so this line is written even on a run where attach returns non-zero, and whether it actually succeeded is read from whether an `attach_failed` line follows it); attach returning (`attach_ended`, with the rc and the session it returned from, written on every way out of an attach before any of the branches that follow it can return); attach exiting non-zero (`attach_failed`, with the rc and which re-attach attempt it was); why a seat went down (`seat_failed`); a warning that the watcher's heartbeat looks stale (`heartbeat_warned`); stepping down quietly on `rein down`'s marker (`seat_stopped`); declining to take a seat because another seat is already there (`seat_occupied`); and each firing of the watchdog that reports the pointer having moved on while attach never returned (`handover_stalled`, one line per firing, carrying the same reason text as the notification -- a notification leaves nothing behind once it's dismissed or missed, so the count of these lines is the only after-the-fact measure of how long the state ran).
- **The three life-cycle events are load-bearing for a second reader, and only as a set.** `seated`, `attach_started`, and `attach_ended` are the only place the seat's connection is written down (the seat lock declares who is seated, not what they are connected to), so `rein status` reads back **whichever of the three came last** to say whether the seat is in step with the current pointer. Taking only `attach_started` answers "where did the seat last go," not "where is it now": from an attach returning until the next one begins -- across resolving the successor, and through an entire wait for a handover, which has no time limit -- that reading reports a connection that does not exist as being in step, which is the same shape as the stall the reader exists to catch. `seated` closes the other end: the log outlives the process that wrote it, so a fresh seat that has not attached yet would otherwise inherit the previous seat's target. Their spellings are held as shared constants rather than literals on each side, so a rename can't leave the reader silently matching nothing.
- **"Cannot be read" is a distinct answer from "nothing is recorded."** The scan stops at the first line that isn't in contract form, having already emitted the lines before it, so a reader that discarded the failure would hand back a target from before the damage and present it as the current one. `rein status` reports that case as its own state and lists the file in `unreadable`.

## Runtime data (markers, locks, request files)

Runtime data is **what belongs to a process currently running on this machine**, and stays confined under each lineage's own runtime directory.

| Path | Role | Writer | Reader |
| --- | --- | --- | --- |
| `<runtime>/handover-request.json` | Handover-request marker | The current primary session requesting the handover (via `rein request`) | watcher |
| `<runtime>/watcher.heartbeat` | The watcher's heartbeat (updated every poll; holds a pid and a timestamp) | watcher **only** | attach loop |
| `<runtime>/watcher.lock/` (holds `pid`) | The resident watcher's watcher lock | watcher **only** | watcher, `rein status` / `up` / `down` / `prune`, `rein request`, hooks (all read-only) |
| `<runtime>/op.lock/` (holds `pid`) | The operation lock that serializes starting and stopping | `rein up` / `down`, `rein prune -f`, `rein request` (held only during publication) | `rein up` / `down` / `prune`, `rein status` / `doctor` (read-only) |
| `<runtime>/seat.lock/` | The seat lock for being present at the seat (holds a pid and its start time) | attach loop | attach loop, `rein status` / `up` / `down` (read-only) |
| `<runtime>/handover.lock/` (holds `pid`) | Mutual exclusion for a handover (the whole sequence of launching a successor and repointing the pointer) | The resident watcher's poll loop, `--bootstrap` | same as writer |
| `<runtime>/watcher.stop` | A request to stop the watcher | `rein down` | watcher (checked every poll, deleted once read), `rein up` / `down` (cleans up any left behind) |
| `<runtime>/seat.stop` | A marker telling the seat that the lineage was shut down | `rein down` (only on the run that stops the primary session) | attach loop (deleted once read), `rein status` (reports presence), `rein up` (cleans up any left behind) |
| `<runtime>/snooze` | The deadline until which a forced handover is postponed | `rein snooze` | The Stop-hooked hooks, `rein status` |
| `<runtime>/handover-ready` | A signal that the session requesting the handover has finished its response (holds `session_id`, one line) | The Stop-hooked hooks | watcher (read during the wait before launching a successor, deleted when the wait ends) |
| `<runtime>/handover-cancel` | A signal that the user spoke up, so the handover is being cancelled (holds `session_id`, one line) | The UserPromptSubmit-hooked hooks | watcher (same as above, plus once more at the end of the round -- a signal that arrived after the wait had been left is reported as `cancel_after_window` and deleted there) |
| `<runtime>/owner` | The runtime directory's owner (the cwd, one line) | Whichever side is preparing the runtime directory (watcher, attach loop, the handover-request writer, `rein init` / `rein up` / `rein snooze`, hooks) | `rein prune`, `rein status --all`, hooks (verifying the owner before reading or writing), the user |
| `<runtime>/token` | This lineage's token -- 64 hex characters, one line, `0600` (see "The lineage token" below) | Whichever side is preparing the runtime directory (the same set as `owner`) | The watcher (puts it in the launch settings), hooks (comparing it against the managed marker), `rein doctor` |
| `<runtime>/processing/<UTC time>-<nonce>.json` | A claimed marker under judgment | watcher | hooks (Stop -- judging whether its own request was already submitted), audit |
| `<runtime>/processed/<UTC time>-<nonce>.json` | Where an accepted marker is moved | watcher | audit |
| `<runtime>/rejected/<UTC time>-<nonce>.json` | Where a marker rejected by freshness validation is moved, and where a stranded item left in `processing/` is recovered to (a rejected run also appends the rejection reason to the record) | watcher | hooks (Stop -- the reason carried in re-blocking a stop), the user, audit |
| `<runtime>/cancelled/<UTC time>-<nonce>.json` | Where a handover request cancelled because the user spoke up is moved | watcher | the user, audit |
| `<runtime>/managed-settings.<nonce>.json` | The launch settings rein hands to a background session it starts (`0600`, created exclusively) | watcher | `claude` (reads it), hooks (deletes it), `rein doctor` |

- **`session_id` never gets mixed into a moved-marker filename** (`<UTC time>-<nonce>` alone is unique). A `session_id` is contractually opaque, and expanding a value containing a path separator into a name could make the `mv` that moves it fail, stranding the marker in `processing/` -- or, if an intermediate directory happens to exist already, **the destination could land outside runtime data entirely, while the watcher still reports success.** **No reader parses the name** (`prune` selects by mtime; hooks and `doctor` read `.session_id` out of the JSON content) -- the name's only job is uniqueness.
- `rein prune -f` takes the operation lock **belonging to the lineage being deleted** (never its own).
- **Replacing a JSON runtime-data file (a marker, `watcher.stop`, `seat.stop`, `snooze`) is always a same-directory temp file plus `mv`** (so a reader never grabs a half-written file). If the destination isn't a regular file, the write **is skipped, fails non-zero**, and one line of reason is left on stderr -- if the destination is a directory, `mv` moves the temp file **into it** and returns 0, so without checking the shape first, the payload would silently land at `<pathname>/<basename>.<nonce>` while the writer reports success (and the reader, reading that pathname as JSON, would have no way to see it never got written). A symlink is rejected for the same reason -- following it would put the replacement somewhere other than the requested pathname, and not following it would just delete the link itself.
- **The watcher claims a marker by `mv`ing it into `processing/` before reading it.** If it read first and moved second, a marker replaced between the judgment and the move could be acted on with its old content while its new content is what gets moved. `mv` is atomic within a filesystem, so only the instance that succeeds at the claim ever handles that request.
- **Cancellation's destination is kept separate from rejection.** `rejected/` means **a defect in the user's own input** that freshness validation (R1-R10) caught; mixing in a request the user spoke up and stopped would leave the audit trail unable to tell "a request that would pass once fixed" apart from "a request the user deliberately stopped." A cancellation gets no reason appended (unlike a rejection reason, there's no defect to fix).
- **Each lineage keeps at most one of each of these two signals -- they never accumulate.** The watcher only acts on a signal whose content matches this request's own `session_id`; one left over from a previous handover is skipped. When the wait ends, both are deleted without requiring a match, and **a failed deletion is never silently ignored** (it would misfire directly into the next handover). The channel that deletes a signal placed after the wait already ended is on the handover-request side (see [the handover specification](handover.md)). The writer places plain one-line text instead of JSON because the watcher is the only reader, and all it needs is `session_id`, and because this avoids adding the external commands an atomic replace needs (`mktemp` and `mv`) to hooks' no-op path -- a half-written, partial line just reads as "no match," and a complete line is readable on the next cycle (this fails safe).
- A marker is **consumed by moving it (`mv`) whether it's accepted, rejected, or cancelled.** Leaving it in place would run the same marker through re-judgment forever, repeating the notification endlessly.
- A failed move **records `failed` and exits non-zero** (treated the same regardless of whether it was an accept or a reject).
- A marker halted by a stage failure (a mechanism-level anomaly) is left in `processing/`. It's never moved to `rejected/`, which would read as "this was rejected."
- **A stranded marker is recovered the next time a watcher starts up** (`mv`ed to `rejected/`, with one `marker_recovered` line left behind). Recovery happens **right after taking the watcher lock** -- the moment this instance becomes the only one advancing that lineage's handover -- so anything left in `processing/` is by definition left over from before. Without a recovery path, a Stop hook that finds its own `session_id` inside `processing/` would keep reading "the handover request is already submitted," and **that session's handover would stop being prompted, permanently** (neither `rein prune`'s cleanup scan nor `rein status` looks at `processing/`, so there's no way to notice either). Recovery isn't a handover itself, so it never launches a successor.
- **Recovery only ever runs when a watcher starts up**, so a state where something is stranded with no watcher around is flagged by `rein doctor` as a WARN (with the count, and a note that starting the watcher will recover it). Neither `rein status` nor the cleanup scan looks here, so that's the only place it's noticed.

## Runtime data hooks use

What hooks place: **a cooldown, a delivery confirmation, a liveness record, a latch, the ledger of running children**, and the fire log shared across lineages.

| Path | Role | Writer | Reader |
| --- | --- | --- | --- |
| `<runtime>/hooks/<session_id>.<kind>` | An advisory's cooldown, and dedup for records | hooks | hooks |
| `<runtime>/hooks/<session_id>.pending-verify` | A record held while an injection's delivery is confirmed | hooks | hooks |
| `<runtime>/hooks/health/last-seen.<event>`, `undelivered`, `error` | A record of whether rein's own hooks are **actually running** | hooks | `rein doctor` |
| `<runtime>/hooks/stop-latch.g<generation>` | A per-generation, persistent latch recording that a stop was blocked (holds the token of the run that placed it) | hooks (only ever created once, via noclobber) | hooks |
| `<runtime>/hooks/stop-latch-rejected.g<generation>` | A latch for the one time a stop-block gets reverted, for a generation whose handover request was rejected | hooks (only ever created once, via noclobber) | hooks |
| `<runtime>/hooks/handover-wait.g<generation>` | A latch for the one line telling the user the wait before the handover has started (see [the hooks specification](hooks.md), "Telling the user the wait has started") | hooks (only ever created once, via noclobber, and only by a run that actually printed the line) | hooks |
| `<runtime>/children/<session_id>.<agent_id>` | The ledger of running children (subagents) -- one file per child, 3 lines: `agent_type`, the epoch it was registered, and the absolute path of that child's own record | hooks (`SubagentStart` places it, `SubagentStop` removes it) | `rein request` (refuses a handover while one is live), `rein prune` |
| `<state root>/hook-fire-log.jsonl` | The fire log of hooks firing -- branches that actually emitted an injection or blocked a stop | hooks | the user, audit, `rein doctor` |

- The cooldown's kinds are `notice` / `handover` / `watcher-missing` / `state-missing-warned` / `stale-warned` / `pct-invalid-warned`; the dedup's kinds are `snooze-logged` / `bg-tasks-missing-logged` / `children-logged` (the first line is the marker, the second is the token of the run that placed it).
- The deadline is held as **an epoch inside the content**, not the mtime, so that a no-op path never has to run `stat` (an external command).
- **Creation is exclusive, via noclobber** -- even if two entry points run in the same turn (the `PostToolUse` compatibility path and `PostToolBatch`), the injection only happens once.
- `pending-verify`'s content is three lines: the matching nonce, the transcript path, and the epoch after which it's valid to judge.
- Health state is **one fact per file** (so interleaved reads and writes never get mixed together). Where the fire log tracks "what did fire," this tracks the anomaly of "not firing" -- registration not taking effect, the launcher unable to trace its target, an injection never delivered -- so it's material for a different judgment, kept in a separate location.
- **The re-block latch for a rejection is kept separate from the normal latch.** The normal latch is consumed the moment the push goes out, but if the watcher rejects the request that was submitted, the marker gets moved to `rejected/` and the state reverts to "unsubmitted." Reusing the same latch would mean that generation's stop never gets blocked again, and forcing a handover would disappear entirely. A re-block happens **only once per generation**, and the message that blocks the stop carries the rejection reason verbatim (every rejection reason is a defect in the request itself, fixable so that it then passes, so carrying the reason is the substance of the re-block). For a generation already re-blocked, the archive location is never read (no external command is added to the no-op path).
- A latch **clears out the ones from lower generations when a new generation is claimed** (the judgment only ever looks at the current generation's name, so anything left behind would never be read again). **One cleanup pass folds away every kind at once** -- splitting it per kind would leave each newly added kind leaking until someone remembered to extend cleanup too. A failed cleanup is ignored -- cleanup never changes a stop decision.
- The fire log is one file shared across lineages -- its line count is exactly the firing record (a no-op path is never recorded). Its columns: `schema`, `at` (UTC), `event`, `decision`, `reason`, `session_id`, `lineage_cwd`, `cwd`, `runner` (its version and the calling convention's version), `selftest`.
- **No payload is ever stored in the log** (secrets could be mixed in). Past 1 MiB, one generation is rotated out to `.1` (rotation happens under a lock; a single-line append is atomic via O_APPEND and needs no lock).
- The temp settings file (`managed-settings.<nonce>.json`) is deleted by the launched session's own SessionStart (see "Settings a background session is launched with" below).
- **The children ledger is partitioned by the parent's `session_id`, and that is what makes it safe.** Leftover entries are unavoidable: stopping the predecessor externally is exactly what a handover does, and a session stopped that way never delivers `SubagentStop` (observed). Every reader builds the prefix out of **its own** `session_id` and looks at nothing else, so residue from an earlier generation can never refuse a later generation's handover -- it is inert by construction, not by how promptly something sweeps it up. **No reader ever splits an entry's name on `.`**: a `session_id` may legitimately contain one (only a path separator and whitespace are rejected), so splitting could attribute one session's entry to another.
- **The ledger is the primary evidence of a live child, and the record's mtime is only the expiry cutoff** (the same two-layer judgment the hooks apply to `background_tasks`). An entry whose child has been silent past `REIN_CHILD_ACTIVE_SEC` doesn't count -- otherwise a child that vanished without delivering `SubagentStop` (its parent killed, the session crashed) would refuse that session's handover forever. Where the record file doesn't exist yet, the moment of registration stands in for its mtime, so a child registered seconds ago is never read as expired.
- `rein prune` treats an entry belonging to a `session_id` **other than the one the current pointer names** as a candidate (see "Structural limits on what `prune` scans" in [the per-verb internal conventions](cli.md)). This is housekeeping only -- it never changes a judgment, since those entries are already inert.

## A seat's presence is read from the seat lock

**Presence is judged by atomically claiming the seat lock (`seat.lock/`) first** (checking whether anyone is there via `ps` and then starting up leaves a window where the other side disappears between the check and the start, or starts at the same instant -- neither is closed off).

- The lock declares **a start time** alongside the pid, so a pid that's been reused is never mistaken for the actual owner.
- A lock with no living owner (left behind by a seat that died) is taken over by the next seat -- the seat is never permanently blocked.
- `ps` is used only to confirm whether the declared pid still exists (as diagnostic material).
- **Why a second seat is refused outright rather than allowed to coexist**: connecting a second terminal to the same session with a plain `claude attach` shares not just the screen but **the input box** -- what one terminal types shows up in both -- so two seats could not do separate work even if both were let in.
- **What a terminal attached that way does at a handover**: once the predecessor session is stopped externally, it prints `Session <id> has exited.` and its own process ends along with it (it never hangs). rein neither manages nor cleans up such a terminal, but it is not left stranded either.

## A resident watcher is one instance per runtime directory (the watcher lock)

Before entering its watch loop, a resident watcher takes `watcher.lock/`; **if it can't, it notifies and exits non-zero** ("another instance is already watching").

- The lock is published by renaming a temp directory holding `pid` (atomic within a filesystem -- the same shape as the operation lock). **The extra declarations are written before publication too** -- writing them in afterward would leave a moment where the lock is published but its declarations aren't all there yet, and a reader hitting that window would treat it as "a lock whose owner can't be confirmed" (under the never-seize discipline, a correctly acquired lock would then sit unconfirmed indefinitely). Besides `pid`, four more things are declared: `start` (the owner's start time, distinguishing pid reuse), `cwd` (what it's watching), `mode` (its role: `watch` / `op` / `handover` / `seat` / `fire-log`), and `token` (the generation that acquired it).
- Whether the owner is actually still there right now is judged from **`pid` being alive and `start` matching** (checking only liveness would mistake a reused pid for the owner, since pids get reused, and that location's lock could never be released again). **Reuse is not a remote possibility**: what caps pid numbering is the numbering ceiling itself, not `kern.maxproc` -- numbers stop below `100000` (a value at or above it is rejected outright as `process id too large`, rather than reading as "not there"), a range small enough that a machine left up cycles through it and hands a lock's old number to something unrelated. A lock with no `start` declared counts as unconfirmable and **defaults to the live side**. If liveness itself can't be confirmed (`ps` isn't answering), that defaults to the live side too.
- Without the lock, the losing side would read the marker right after the other side consumed it, and log a rejection under the wrong reason -- **`R1 cannot be parsed as JSON`** -- to the audit trail.
- The `pid` inside a lock is whatever its owner declared, and **only a stale lock -- one confirmed to have no living owner -- ever gets retaken.** Stale comes in two shapes: the declared pid is gone, or **the pid is alive but doesn't belong to the watcher watching the target cwd** (pid reuse). Both count as "confirmed all the way down to identity," so a reader also reads this as **not running** (`status --json`'s `.watcher.state` reports `stopped`). If only the acquiring side read this as "watching," startup would stay blocked forever in a state readers see as "gone," and that location could never hold a handover again. Identity confirmation goes through the same shared-library function on both sides, so the acquirer and the reader never classify a lock differently. **Confirming identity is done from the lock's own declarations**: if `cwd` doesn't match the target, it's read as "something else is alive here" and left unseized; if `mode` is anything other than `watch`, it's read as "not a resident role" and left unseized. **Scanning `ps`'s command line only happens for a lock with no `mode` declared** (something rein never published -- placed by hand). A command line can't distinguish an option from an option's value, so making a full-line scan the routine condition would let a word inside some value flip the judgment. Where the scan does run it can rely on having the whole line: `ps -p <pid> -o command=` is never truncated to terminal width, not even through a pipe (an argv well past 300 characters comes back as-is), which is why the material that identifies a watcher -- its real file's path and `--cwd <cwd>` -- is placed on the command line in the first place. A lock whose `pid` can't be read, or isn't a number, is **left unseized and exits non-zero** (an implementation that seizes an unconfirmable lock is indistinguishable from a double-launch itself).
- A lock owner's liveness is judged **only by reading `ps -p`** -- **this module never runs an OS-level process-termination operation (`kill` / `pkill`, and so on) at all**. The one exception is **`claude stop`** at the end of a handover -- an external stop directed at the CLI, not an operation that kills an OS process directly.
- The lock is **released on both a normal exit and a stage failure** (removed via `trap`). It's left behind if killed by a signal, but the next startup retakes it as a stale lock.
- **Releasing checks `token` and only removes the lock from its own generation** (a lock retaken by a different run is never touched). **"Couldn't release it" and "it isn't mine" are returned as distinct outcomes** -- collapsing them into the same value would make even a correct, deliberate step-back (because a different generation had already retaken it) get flagged by the caller as a mechanism-level anomaly.
- **Retaking a stale lock is limited to the exact lock -- identified by `pid` -- that this run itself judged stale**: the published name is renamed to a temp name, the `pid` inside is checked, and if it doesn't match, the temp name is renamed back and this run steps away. In the window between checking and removing, a different run may already have removed that same stale lock and **retaken it**; a plain release would then be able to strip a lock that just became live again (two runs holding the lock at once).
- `--bootstrap` never takes this lock (it's a separate, one-shot entry point that needs to be usable at the same time as a resident watcher).
- **Whether the watcher is resident is judged by exactly one thing, read from this lock**: `pid` is alive, and its identity is a resident watcher watching the target cwd (the `--bootstrap` entry point is never resident). Readers are `rein status` / `up` / `down` / `prune`, plus `rein request` (which never writes a marker if it's absent) and hooks (which never stays silent about an already-submitted request if it's absent), and the watcher's own lock acquisition -- **the judgment's implementation lives in one shared-library function** (writing it per reader would let one reader read "there" while another doesn't).
- **The judgment splits along whether this could be confirmed at all.** No lock; the owner's pid is gone; or the pid is alive but its identity isn't the watcher for the target cwd (pid reuse) -- all three read as **not resident** (`.watcher.state` reports `stopped`; the latter two are stale locks). **Can't be determined** (`.watcher.state` reports `unknown`) is reserved for the case with no material to work from at all -- `pid` unreadable, not a number, or the owner's cwd can't be traced. Putting a lock whose identity was confirmed into the can't-determine bucket would split the acquiring side (which retakes it as stale) from the reader (which refuses to start) into two different classifications.

## The watcher's heartbeat

A resident watcher **updates `watcher.heartbeat` on every poll**, and if it can't write it, records `failed` and exits non-zero.

- **It keeps updating even while a handover is in progress** (the wait loops confirming the successor launched and confirming the predecessor exited) -- one handover can take as long as `launch_timeout_sec + exit_grace_sec + stop_timeout_sec` in the worst case, and stopping updates during that would make the heartbeat look stale to a waiting seat, flagging a watcher that's processing normally as "possibly stopped."
- The wait loops aren't the whole handover: between them the watcher runs **blocking external commands in the foreground** (`claude --bg` to launch the successor, the enumeration that resolves the predecessor's job handle, `claude stop`), and nothing writes the heartbeat while one of those is running. So **the heartbeat is written immediately before each of them**, which bounds how stale it can get to that one command's own cap instead of the whole stretch. A blocking call can't be interrupted to write partway through, and this module never runs an OS-level process-termination operation, so a background refresher that would have to be killed afterwards is ruled out -- writing before each call is the whole of the mechanism. A heartbeat that can't be written there is a stage failure, exactly as inside the wait loops.
- The attach loop checks its freshness **only while waiting for a handover.** If it's older than `seat_heartbeat_max_age_sec` (default 60 seconds; `0` disables the check) or the file is missing, it notifies "the watcher may have stopped" (since dropping the seat would close the user's own terminal, one absent cycle alone never steps down; the notification fires at most once per wait, while the counting behind it keeps going silently).
- **Three consecutive absent cycles cut the wait short and step down non-zero, with a reason and how to restart included** (this consecutive-count isn't an operational parameter, so it has no settings key). A wait with nothing left to drive the handover can never succeed, so while waiting indefinitely stays the design, only a wait that can never succeed gets shut down. A single fresh heartbeat read even once breaks the streak (a single miss right as the watcher restarts never steps down the seat). This judgment sits **after every other material for that cycle has already been checked** -- the pointer changing, a `seat.stop` marker, the target disappearing -- so if there's still something that could make progress, that takes effect first.
- Without this, the attach loop has no way to tell whether "the pointer hasn't changed" means **the handover just hasn't arrived yet** or **the watcher is dead**.

## The watcher is stopped via a request file (`watcher.stop`)

Since this module never performs an OS-level process-termination operation, the entry point that stops a resident watcher (`rein down`) works the same way: **place a stop-request file and let the watcher step down on its own.**

```json
{"schema":"rein.watcher-stop.v1","requested_at":"2026-08-16T04:12:33Z","requested_by_pid":12345}
```

- The writer is `rein down` **and no other**. Before placing it, it confirms that `watcher.lock/`'s `pid` is alive and that `ps -p <pid> -o command=`'s identity is actually rein's watcher (**pids get reused**, so skipping the identity check could leave a stop request against an unrelated process's lineage).
- **A partial match isn't enough** for this confirmation -- it checks three things: the watcher's actual path (`scripts/rein-watcher.sh`'s absolute path), `--cwd <target>` (checking through the trailing whitespace to rule out a prefix match), and the absence of `--bootstrap`. Reading a process whose command line merely contains the name (an editor, `tail`, a watcher for a different cwd) as the watcher would leave a stop request against that process's own lineage.
- The watcher checks this request **every cycle**, and checks it **after processing markers** -- checking it first could let the watcher step down without ever acting on a handover request that arrived in that same cycle.
- The watcher accepts a request only **after validating it against the specification exactly** (`schema` is `rein.watcher-stop.v1`, `requested_at` matches the required format, `requested_by_pid` is a positive integer). A malformed request is **never deleted** -- one line of reason goes to `watcher.log` and monitoring continues (deleting it would make it indistinguishable from an accepted request, from the writer's point of view).
- The watcher **deletes the request before exiting** (skipping this would make the next startup step right back down from the same leftover request). If the delete fails, it never proceeds to a successful stop -- it leaves a reason and **exits non-zero**. The exit reason is left as one line in `watcher.log`.
- After placing the request, `rein down` waits until **both the watcher's pid is gone and the request file is gone**, and **surfaces this non-zero** if the two haven't both happened by `cmd_timeout_sec` (never leaving behind the illusion of "I thought I stopped it"). A run where only the pid is gone but the request is still there is returned distinctly, as "exited before the request was accepted." This module has no further recourse from there, so it's handed back to the user.
- A leftover request (from `down` timing out, or the watcher dying by signal) is **deleted the next time `rein up` takes the operation lock, with one line reported** (with no cleanup at all, the next watcher started would just step right back down on its first cycle).
- **Even on the path where `down` returns "the watcher isn't there," it still runs the same cleanup before calling it a success** -- only having both "no pid" and "no leftover request" together actually means it's stopped, so success is never defined differently per path. `rein status`'s "stop request" line shows whether one exists.
- This only stops the watcher (`rein down --watcher-only` ends here). If a seat is still running, it just reports that fact along with how to step down (`Ctrl-C` in the terminal).

## Shutting down a lineage is signaled to the seat with a marker (`seat.stop`)

`rein down`'s default is to **externally stop the primary session too, after the watcher**, so a seat that had been attached gets its attach call returned. From the seat's own view, "attach returned but the pointer never changed" would normally be an anomaly (a handover stalled partway), so the fact that this was an intended stop gets communicated with **a marker**.

```json
{"schema":"rein.seat-stop.v1","requested_at":"2026-08-18T04:12:33Z","requested_by_pid":12345}
```

- The writer is `rein down` **and no other**; the reader (which also deletes it) is the attach loop **and no other** (the same one-directional relay as the stop request).
- **It's placed before the external stop.** Placing it afterward would open a window where a seat whose attach already returned reads no marker at all and reports it as an anomaly.
- The seat checks for the marker when attach returns (and on each cycle of a handover wait); if it's there, it **deletes it, prints exactly one line to the terminal, and exits 0** (no GUI notification -- since the user is the one who ran the stop, the person it needs to tell is already sitting at the terminal).
- The seat consumes it only **after checking it matches the contract's format** (`schema` is `rein.seat-stop.v1`), so it never quietly steps down over something that merely shares the same filename.
- **Cleanup (deleting it and nothing else) never checks the format** -- since its purpose is just "make anything left behind go away," it's held to a different discipline than consumption (reading it and stepping down). `rein status` reports a malformed marker as "the seat won't consume this -- the next seat to sit down, or `up`, will clean it up."
- **The next seat never consumes a stale marker.** A seat deletes whatever marker was already there right after taking the seat lock, and `rein up` deletes whatever was already there right after taking the operation lock, reporting one line (the same discipline as `watcher.stop`'s cleanup).
- But the cleanup a seat does before attaching **skips deletion if the marker's `requested_by_pid` is alive and its `requested_at` falls within the window** (`cmd_timeout_sec + stop_timeout_sec`). Checking only one of those (pid liveness alone) could mistake an unrelated process that got assigned the same number after `down` finished (pid reuse) for the owner, leaving the marker behind permanently -- the next seat to sit down would then consume it on its very first attach-return and quietly step down. A timestamp in the future (from a clock adjustment mid-run) is never treated as "old" -- the side that keeps a user-initiated stop's marker intact is chosen instead. If `rein attach` from a different terminal arrives in the window between `down` placing the marker and the external stop actually taking effect, that seat could delete the marker, and the user's own stop would then be reported as a failure the moment attach returns right after (a seat only holds the seat lock, and isn't serialized against `down`'s operation lock). `rein up`'s side sits under the operation lock and never enters this window, so it doesn't check liveness at all.
- Even on a run where the external stop fails, or where it doesn't finish within the cap, the marker is **never deleted** (it gets cleaned up before either the next `up` or the next seat arrives). `rein status`'s "seat stop" line shows whether it exists.

## A handover is serialized by the handover's own exclusive lock (`handover.lock/`)

**Two entry points can advance a handover** -- a resident watcher's poll loop (processing an unconsumed marker), and the one-shot `--bootstrap`. `rein up` starts the watcher and then runs bootstrap under that same operation lock, so for one lineage, the two **run at the same time**.

- Without this exclusion, `rein up` run against a lineage with an unconsumed handover-request marker could launch **two successors for the same generation** (the pointer is written **only after** the successor's launch is confirmed, so bootstrap's own defense -- "abort if the pointer already points at a live session" -- passes right through that window). Whichever side never made it onto the pointer would keep editing the same working tree, unstopped by anyone.
- Neither the watcher lock nor the operation lock can substitute for this (the former is held for as long as the watcher is resident, the latter for as long as `up` runs, so the watcher `up` started and `up`'s own bootstrap would always collide) -- so it exists as **a third lock, scoped just to a handover's own span**.
- Whichever side can't take it **yields without launching anything**. The watcher re-checks on its next cycle; bootstrap notifies with a reason and exits non-zero.
- A lock with no living owner (stale) gets retaken (the same discipline as `up` / `down`) -- a single crash mid-handover never permanently blocks that lineage.

## Starting and stopping are serialized by the operation lock (`op.lock/`)

**`rein up` / `rein down` both check whether the watcher is resident before starting or stopping it, so they're serialized by an operation lock separate from the watcher lock** (running at the same time could let two `up` runs both read "not there" and start the watcher twice).

**`rein request` takes this same lock too** -- if checking "no unconsumed marker exists" and publishing the marker were separate steps, two requests fired at once could both read "none unconsumed" and the one that wrote second would replace the first, silently, with no non-zero and no record. It also keeps requests from interleaving with `up` / `down` (publishing in the window between `down` stopping the watcher and releasing the lock would leave a marker sitting at a location with no watcher, while still reporting success with 0). It's held only for the publishing step itself; the side that can't take it falls back to the existing "an unconsumed marker already exists" path (see "The only way to write a marker is `rein request`" in [the handover specification](handover.md)).

- If the owner's `pid` is alive, it never yields -- it exits non-zero; a lock whose `pid` can't be read is **never seized** (an implementation that seizes an unconfirmable lock is indistinguishable from a double-launch itself).
- `up` releases the lock before moving on to the seat layer (the attach loop).
- **The lock is published so that a state with an unconfirmable owner can never even be generated in the first place** (the same as the watcher lock). A two-step implementation -- `mkdir`, then write `pid` -- would leave a lock that crashed or failed to write in between as "a lock with no confirmable owner," which under the never-seize discipline could never be released, no matter how much time passed (every subsequent `up` / `down` would be permanently blocked). The actual implementation publishes a temp directory that already has `pid` written, via rename -- a published lock always already has `pid`.
- **Releasing it is likewise a single step.** Deleting `pid` and then `rmdir`-ing would leave a published lock with no `pid` behind on a run that crashed between the two, or on one where `rmdir` fails (something rein doesn't recognize is inside, say) -- the release side would then be creating the exact unconfirmable state the acquire side worked to rule out. Instead, the published name is renamed away and then removed along with its contents.
- For the case of still ending up stuck with a leftover lock, `rein doctor` and `rein status` both show the operation lock's state in one line, and the message explaining a refusal includes how to remove it (`rmdir <path>`).

## Settings a background session is launched with (assembled by rein)

A session rein launches (the first one, or a successor) is handed **a single object layering two things on top of the user's own `settings`**, via a temp file (under the runtime directory, `0600`, created exclusively). Passing `--settings` twice makes the later one win (observed directly), so laying the user's own settings and rein's settings side by side isn't an option.

| What gets layered on | Why |
| --- | --- |
| `worktree.bgIsolation = "none"` | By default, a background session launched at a cwd under git ends up branching its edits into `.claude/worktrees/`, taking both the successor's work and the lineage's own records off the real tree |
| The managed marker's `env` | The marker lets hooks confirm the lineage without re-deriving it from cwd |

- Disabling isolation is **something rein applies only to the session it launches itself** (it's never written into the user's own settings).
- **Before calling `claude`, the launch drops the lineage's own isolation environment variables** (`REIN_CONFIG_FILE` / `REIN_RUNTIME_DIR` / `REIN_RECORDS_ROOT`) -- a background session's hooks inherit their environment from the shared background service (observed), so if a lineage moved via `--root` is the one that first starts that service, its values would stick around for every background session in every generation after it, running hooks that keep pointing at a different lineage's location. The lineage's context is already carried by the managed marker (`env`) below, so dropping these never breaks how a successor resolves it.
- The managed marker **carries the lineage's entire context** -- cwd and the runtime directory, plus the user config and records location, neither of which can be derived from cwd -- so hooks see the same location even for a lineage moved via `--root`. It also carries **this lineage's token**, read out of `<runtime>/token` at launch and never redrawn there (see "The lineage token" above) -- the one field of the marker that a settings file naming the same lineage could not have supplied. This can't be delivered via the launch command's environment variables (a background session's hooks inherit their environment from the shared background service -- observed directly), so it's carried in settings' `env` instead. The marker's individual values and validation are in [the hooks specification](hooks.md).
- If the caller's `settings` can't be read as a JSON object (an array, malformed JSON, a path that doesn't exist), the launch **fails before starting, without silently rounding it off** (it never launches with isolation still in effect). The value itself is never shown, either in a reason message or on a command line (`settings` can contain credentials). `rein doctor` surfaces the same judgment ahead of time, so this is never something only noticed right before launch.
- The temp file is **deleted by the launched session's own SessionStart.** The deleting side is the launched session and not the watcher **because the file's path reaches that session only through the marker's `env`** -- so the file disappearing is itself proof that the marker arrived and was read, which is exactly what the watcher waits on before moving the pointer (see "Current pointer" in [the handover specification](handover.md)). One still sitting there is a sign that the launched session never came up, and `rein doctor` reports where it is.
- On a machine where the organization managed settings (`/Library/Application Support/ClaudeCode/managed-settings.json` on macOS) force isolation to a different value, the launch **fails before starting.** The judgment lives in one shared function, and **all three paths -- `rein up`, `rein doctor`, and the watcher's own launch of a successor -- go through the same one** (a machine where diagnosis passed but the actual launch still failed never happens).
- What this can judge is limited to a machine where that file is readable and a value is actually written in it -- **precedence itself can't be confirmed from outside.** On a machine where managed settings enforce this, confirm once, for real, that a successor can actually write to the real tree before relying on it operationally.
