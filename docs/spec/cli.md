# Per-verb internal conventions

Internal conventions each verb's implementation follows: installation, delegation, short-form assignment, plugin cache and updates, launching the watcher directly, what `doctor` inspects, and what `prune` scans.

## Installation (`init`)

**`init` runs the following 5 steps in order and leaves it to `doctor` to judge whether installation succeeded** (the same judgment doesn't live in two places).

| Step | What it does |
| --- | --- |
| 1 | Symlink `~/.local/bin/rein` to this repository's `bin/rein` |
| 2 | Enable the plugin at user scope (register the marketplace, then install with `--scope user`) |
| 3 | Set up that project's runtime data location (the runtime directory, its owner file `owner`, and its lineage token `token`) |
| 4 | Place a non-empty template at `handoff_path`'s effective value |
| 5 | Run `rein doctor` |

- **Keep a single real file** (never let an update take effect on only one of two copies): the PATH command is a symlink, and `doctor` checks that installation and the real file match.
- **The Claude Code CLI is resolved before step 1 touches anything.** Steps 1, 2 and 5 all go through `claude`, and the first one that actually reaches for it is the plugin's enablement-state query -- so on a machine without the CLI, `init` stopped on "cannot read `claude plugin list --json`", naming the query rather than the missing command and sending a user with nothing installed off to look at a plugin registry that was never the problem. **"The CLI is not here" and "the CLI is here but its answer cannot be read" are separate reasons with separate fixes**, so the first is checked up front by resolution alone (whether a resolvable CLI actually works is what the query that follows judges, so probing it here would only double the calls). It is checked **before step 1** for the same reason the exact plugin ID is built first: a machine that cannot get past it must not be left with the symlink placed and nothing else done.
- **Step 3 sets up the location a lineage's runtime data lives in**, including its owner file (`<runtime>/owner`), which is what every entry point checks before reading or writing there, and its lineage token (`<runtime>/token`), which is what a session's hooks are checked against (see "The lineage token" in [the locations specification](runtime.md)). A location claimed before tokens existed carries only the owner file, so `init` treats "already set up" as **both files present** and places the missing one rather than reporting that lineage as finished. It is not what makes hooks fire: hooks act only on a session rein itself launched, told by the managed marker env (see "A window rein didn't launch gets no action from hooks" in [the hooks specification](hooks.md)), so nothing fires until `rein up` starts a session -- even though installation and plugin activation are both already done. Runtime data is **something rein owns**, so this doesn't contradict the principle that `init` only creates what it owns. Setting it up goes through the same one shared function as the other entry points (`up` / seat / `request` / hooks), and `--dry-run` skips creating it.
- **Steps 3 and 4 are per lineage**: both take effect only for the one lineage named explicitly by `--cwd`, so run them once per target project (omit `--cwd` and they land on the lineage of wherever you ran the command, so the intended target is left with nothing and the first session's launch there fails). Steps 1 and 2 only need to run once overall; later runs are idempotent no-ops.
- **`init` does not register the usage writer (statusLine)**: `settings.json` is the user's own, and `init` only creates what rein owns. `init` tells the user in one line that this is theirs to do; the final `doctor` step reports whether it's registered and, if not, prints a paste-in example.
- A symlink that already points at the same real file is left alone. **One that points at a different real file fails instead of being overwritten** (never hijack a lineage that's using a different checkout without the user noticing -- to replace it, remove it by hand).
- The marketplace name is taken from `name` in `.claude-plugin/marketplace.json`.
- If something already occupies the template's location in **a shape the handoff document can't be accepted in** (a symlink, a directory, an empty file), this fails instead of passing it through as "already there." The acceptance rule is the same one the first session's launch and handover requests use -- letting it pass would make `init` succeed while only handovers break later.
- What the template writes is only rein's own semantics: one sentence saying this is the one handoff document that reaches the successor at launch, **the section headings the successor reads**, and, in parentheses, instructions for how to write each section. The content itself belongs to the user side; rein never reads it. **The canonical source for the section structure is the shared library's list**, and the template (the heredoc in `scripts/lib/cli/init.sh`) is a dependent copy of it -- `init`'s self-check cross-checks both directions (a missing section, an extra heading not in the list). **If only one side moves, the check fails, so the list is always the one to fix.** Neither this document nor the README enumerates the section names: adding another copy of the same thing just means the prose goes stale once the real count changes (it once said 2 headings while the real template had grown to 4). The reader-facing procedure lives in the skill instead. **The rule for how to write the handoff document** is likewise a single value in the shared library, but this one keeps no copy at all -- it **fills in by generation**: the heredoc is split in two and the value is printed in one line between the halves (the same value also fills hooks' three firing points -- see [the hooks specification](hooks.md)). The self-check only confirms that generation took effect and the value landed in the template; it doesn't cross-check by enumerating key words, since an enumeration would just let a newly added rule slip through unnoticed.

### `init` does not create a config template

Unset settings run on their defaults, and the design has the consumer fail loud if something it needs is missing -- so **placing a template would erase the distinction between "default" and "explicitly set" from the very first run.** Settings get added with `rein config set` once they're actually needed.

- **The handoff document is the one exception**: `init` places a template for it, because "it exists and isn't empty" is a precondition for handover (the first session's launch's existence check, and freshness validation) -- if nobody creates it, the first session's launch itself never comes up.
- Placing the handoff document's template doesn't itself change behavior, and it doesn't create a "default vs. explicit" distinction either -- that's what sets it apart from config.

## Delegation (`request` / `attach` / `bootstrap`)

Before delegating, `bin/rein` **reads config through to completion and validates it**, then launches the target script with the resolved `--cwd` prepended. The target script accepts the same flags as-is, so passing the same flag again afterward lets the user's own value win.

- **Effective values never travel through environment variables.** The delegate reads the config layer itself (the watcher does so every poll cycle), so putting a value in the environment would pin every later re-read to whatever it was at launch.
- Verb arguments that flow straight through to the delegate accept only their long form -- interpreting short forms is closed inside the verb itself.
- **`bootstrap` is an internal entry point**: dispatch keeps it, but the user-facing command help (`rein help`'s usage) doesn't list it. Launching the first session runs through `up`, so it isn't a verb the user types directly.
- **There is no verb for calling hooks**: the registry calls the launcher inside the plugin directly, never passing through CLI dispatch at all (the three-step execution path is in [the hooks specification](hooks.md)). A compatibility adapter from when an older registry called `rein hook <event>` was removed verb and all, after confirming that registration no longer existed in the user's own plugin cache.
- **What goes into the user-facing command help (`rein help`) is outside this document's scope.** The developer-facing internal conventions and the user-facing help serve different readers and purposes, so the set of verbs each one lists is deliberately asymmetric (`bootstrap` exists in dispatch but appears in neither help nor guidance). Letting this document dictate help's content would let a spec's own concerns leak into help's shape.

## Short-form assignment conventions

**The canonical source is `rein_cli_aliases` in `bin/rein`** (the user-facing table is built from it). Command help writes the short form folded into each line (`-C, --cwd <path>`), so there's no path that generates it from the table -- **selftest cross-checks the table against help entry by entry to keep them in sync.**

- New assignments follow existing CLI conventions (`-C` for git's working directory, `-F` for ssh's config file, `-n` for dry-run).
- Lowercase `-d` has settled on the meaning "detach from the foreground" (`docker compose up -d`), so it's assigned to `up --detach`, and **it isn't used for naming a location** (that's the uppercase `-D`). `-r` also carries the meaning "recursive," so a location gets `-R` too.
- **The list of assignments itself lives in `rein help`** (each line shows both the short and long form) -- this document only holds the rationale, so the same list isn't written in two places.
- **An irreversible delete removes nothing without `-f, --force`** (flags that choose the target are free to have short forms). A single mistyped character never turning into a delete is guaranteed not by withholding short forms, but by keeping the actual execution behind a single gate.
- Interpretation is closed per verb so the same single letter can carry a different meaning in a different setting.
- The selftest pins down four things: **the table and the implementation correspond** (checked both ways), **the same letter never carries two meanings in the same setting**, **the short and long form produce the same result**, and **for each table entry, command help's matching line contains both the short and long form as words** (this check stands in for the generation path that doesn't exist). The join format itself isn't pinned down -- what matters is that the correspondence can be read, not how the separator is written.

## Plugin cache and updates

Installing the plugin makes a copy under `~/.claude/plugins/cache/`, but **which side is read at runtime depends on how it was installed** (the two shapes, and the scope each one covers, are in the bullets below). To make an update take effect, run `claude plugin update rein@claude-rein` (**give the exact ID** -- the short name alone fails with "not found").

- **When the source is a local directory, the bundled files that get read are the real ones at the source** -- a change to the registry (`hooks/hooks.json`) takes effect without reinstalling. **Treat an install whose source is git as running off a copy** (you update it, but the stale copy is what runs). **Which side gets read rests on observation, not on a documented guarantee**, so it can change with a Claude Code version -- and the observation only covers a local-directory source, which is why a git source is treated as a copy rather than measured.
- **So that an implementation update takes effect regardless of which side is read, the plugin side holds nothing but a minimal launcher** -- the hooks implementation lives at the symlink's target (this repository's `scripts/rein-hook.sh`), so even when the copy is what's read, an implementation update takes effect without reinstalling. The three-step execution path and the calling convention's version live in [the hooks specification](hooks.md).
- Registering a local directory as a marketplace requires `.claude-plugin/marketplace.json` (without it, registration fails on the spot).
- Whether it's installed, and its actual `id` (`<name>@<marketplace>`), are confirmed with `claude plugin list --json`. In an environment where that can't be read, the check **fails as undetermined** (it never passes silently).
- The migration steps for a user who has the same advisory registered in their own settings (something the user does themselves) are in the registration section of [the hooks specification](hooks.md).

## Launching the watcher directly

**`rein up` is the entry point for launching the resident watcher.** Running `scripts/rein-watcher.sh` directly also works, since either path reads the config layer for itself, but it drops two disciplines.

- **Launch it with an absolute path.** `status` / `up` / `down` match the command line against an absolute path to avoid mistaking a reused PID for the watcher, so a watcher launched with a relative path fails that match and reads back as `not running` (a stale lock from PID reuse). Run `rein up` in that state and **it retakes the lock and starts a second watcher** (the discipline is to retake any lock the match judges to belong to a different process) -- so even the direct path should launch with an absolute path.
- **The direct path never takes the operation lock**, so serialization against `prune -f` doesn't apply -- use `rein up` whenever there's a chance it could launch at the same time as cleanup.

## Remaining per-verb conventions

**One remaining convention per verb** (the discipline for locations, locks, and the hooks side lives in each of the related documents).

- **`up` and `down` are idempotent operations that bring a lineage's three layers (the resident watcher, the primary session, and the seat) to either present or absent**, and a partial run is chosen with flags (`up --detach` / `up --no-bootstrap` / `down --watcher-only`) -- giving each layer its own verb would leave the caller to work out how much of it exists.
- `up` serializes the whole thing with the operation lock, and clears out any leftover stop request or leftover seat-stop marker here (the lock and request file discipline is in [the locations and locks specification](runtime.md)). It waits to see the watcher actually come up (the watcher lock's appearance) before returning, and fails -- naming where the watcher log lives -- if it doesn't.
- `up`'s seat layer **looks different from the other two when it's already present**, but the discipline is the same: report it and exit 0. The delegate (`rein attach`) refuses when a seat is already present and returns non-zero, so `up` checks presence itself before delegating and branches on it (`attach` on its own keeps refusing as usual).
- The step of `down` that stops the primary session is fail-loud: failing to resolve the short job ID, `claude stop` returning non-zero, and not disappearing from enumeration within the cap all exit non-zero with a reason (never leaving a "thought it stopped" state). The watcher is stopped first because a handover running mid-stop would launch a successor to a primary session that's already been stopped.
- `up` discards the watcher's stdout and stderr because **the same fact shouldn't live in two places** -- the watcher log is where the operational record belongs.
- **An irreversible-delete entry point defaults to a preview and opts into execution with `-f, --force`; every other verb defaults to execution and opts into a preview with `-n, --dry-run`** (`prune` and `init` having opposite defaults follows from this rule -- it isn't a per-verb whim).
- A script reads the watcher's liveness through two fields of `status --json`: **`.watcher.process_state` for whether it's resident as a process, and `.watcher.state` for the overall picture that folds in heartbeat freshness too** (the verb that used to return this as an exit code has been retired). They're split in two so a reader can tell "not there" apart from "there but stuck": right after `rein up -d`, when only residency matters, the heartbeat hasn't been written yet and `.watcher.state` can read `unknown`, so check `.watcher.process_state` instead (`.watcher.state`'s range is four values: `running`, resident with a fresh heartbeat; `stale`, resident but the heartbeat is older than the cap; `stopped`, not resident; and `unknown`, nothing to judge from). "Not there" (`stopped`) and "nothing to judge from" (`unknown`) are kept as separate values so a script can tell them apart -- and if the preconditions for judging it (config, resolving the location) aren't even met, it returns a non-zero exit instead of a value at all.
- `status --json` carries the full list of generations so the human-readable display and the machine-readable form don't get mixed into the same path.
- **A record that could not be read is named in `unreadable`, and "could not be read" includes an empty read.** `jq` prints nothing at all when it gives up on its input, so the most ordinary way a record breaks -- one caught half-written -- reaches the assembly as the same empty string a file that was never there would produce. Folding both into a silent `null` left `--json` alone answering "there is no stop request" for a stop request sitting right there unreadable, while the human-readable view called that very same file present -- the one form a script reads being the one form that went quiet. **Each place a record is taken declares which of the two an empty read means for it**, and a place that declares neither is listed as unreadable rather than having a meaning picked for it. The two log lines (`last_event`, `seat_last_event`) are the ones where empty legitimately means "nothing recorded yet" -- a lineage that has not handed over, a seat not yet sat in -- which the human-readable form answers `none` for, so the two forms stay in step.
- The status view prints **the handover log's last line and the seat log's last line as separate lines** (the event and timestamp for a human reader; the line itself, or `null` if there is none, for `--json`). The handover log alone can't tell you that the watcher is running while the seat isn't holding its place.
- **The seat line reports two separate things: that a seat is present, and what it is connected to.** The seat lock declares only who is seated (pid, start time, cwd), so presence on its own reads exactly the same whether the seat is following the current pointer or has been stuck on a session the pointer left behind (observed: a seat held on the predecessor for over 4 hours while status reported a plain `attached`). What it is connected to comes from **the last of the seat log's three life-cycle lines** -- `seated`, `attach_started`, `attach_ended` -- compared against the same contract-validated pointer read the rest of the view already did. Reading `attach_started` alone would answer "where did the seat last go," not "where is it now," and those differ for the whole of every ordinary wait for a handover (no time limit on it), which would report the accident's own shape as healthy. The line says which of **five** states it is in: `connected to <id>, matches the current pointer`; `connected to <id>, but the current pointer is <id>`, followed by the one instruction that ends that state; `connected to <id>, cannot be compared against the current pointer`, when the pointer could not be read at all; `not connected right now`, when the last line is `attach_ended` (the seat is between attaches -- resolving the successor, or waiting for a handover); and `not connected yet`, when the seat has sat down but has never entered attach. `--json` carries the same reading as `seat.connection` (`attached` / `between` / `none` / `unreadable`), `seat.attached_session_id`, and `seat.pointer_match` (`null` wherever there is nothing to compare -- including every state but `attached`), so a machine reader can't keep concluding the seat is fine in exactly the state the human-readable line calls out. **A seat log that cannot be scanned is its own answer** (`unreadable`), listed in `unreadable` alongside every other record that isn't in contract form: jq stops at the first malformed line having already emitted the ones before it, so folding that case into "nothing recorded" would hand back a stale connection target and present it as the current one.
- **The handoff document's section structure is exposed through `--json` too**: `handoff.sections_ok` (a boolean) and `handoff.sections_reason` (naming what's wrong, or `null` if there's nothing to say). `handoff.present` only ever says "exists, in an acceptable shape" -- but a handover request is always rejected when the section structure doesn't match the template, so a machine reader that conditions only on `present` reads "the handoff document is there" and then fails at handover time (the human-readable line and `doctor` never carried this same asymmetry). **This is surfaced as a separate key rather than folded into the acceptance judgment (`present`)** for the same reason status and `doctor` are: so that no path other than a handover request changes meaning. **A run that never reads the sections at all (`present` is `false`) sets `sections_ok` to `null`** -- reporting something unmeasured as "fine" would let a reader who skips `present` read a lineage with no handoff document as green (the reason nothing was measured is already carried by that same object's `present`, so it isn't copied into `sections_reason`).
- `attach` / `down` / `snooze`'s internal discipline (the presence lock; handing off the stop request and the seat-stop marker; the snooze deadline) is in [the locations and locks specification](runtime.md) and [the hooks specification](hooks.md).

## What `doctor` inspects

**`doctor` reports separately on whether it's installed and whether hooks are actually running** (so it never shows green for the broken shape where registration exists but stays silent).

| Facet | What it checks |
| --- | --- |
| Dependencies | Prerequisite tools, resolving the `claude` command, the usage record's location |
| Usage writer | The `statusLine` registration in the user's own settings; **for a lineage that has the bundled writer registered, one trial run of it** (can it write a record matching the contract to an isolated, temporary location -- this never lets "registered but failing to run" pass as green); the newest record's format and freshness at the location (see [the usage record specification](usage-state.md)) |
| Installation | Whether `rein`'s real file matches; **whether `rein` can be called from PATH**; plugin activation; **whether the marketplace distributing the plugin's real file is this work tree** |
| Hooks path | Whether the registered command calls the launcher; whether the launcher and runner are executable |
| Hooks activity | Last firing per event, unreached events, internal errors |
| Fire log | Missing, last line too old, grown past the cap and never archived, the breakdown of events and judgment kinds, the breakdown of schema/event pairs, the count of unparseable lines, the count of lines with an unknown schema |
| Launch | Whether launch settings can be assembled; whether the organization managed settings force background-session isolation |
| Locations | The runtime directory's owner; **its lineage token** (missing is `WARN` with the command to place one -- the next `rein up` resolves it, including for a location claimed before tokens existed; a mode other than `0600` is `FAIL`, since hooks still work while the value other users could read is exactly what makes a marker unforgeable); a leftover operation lock; leftover launch settings; a nested lineage; guidance about an old-format watcher log; **a handover request stranded in `processing/`**; **a location rein writes to that exists but can't be written** (none of them existing yet is `WARN`, not `OK`) |
| Handover state | The shape where only the last step of a handover is left standing (`WARN`), and **the shape where the primary session on record is absent from enumeration while the predecessor is alive** (`handover_mismatch`, `FAIL` -- a state deliberately never auto-fixed, so this line naming it and how to fix it is the only way out) |

- **Plugin identity is checked by exact ID (`<name>@<marketplace>`), and goes further to check the marketplace's real file too**: even with a matching ID, if a same-named marketplace points at a different checkout, the hooks that actually fire belong to a different real file (doctor reads all green, yet not a single hook in this work tree ever fires). The real file is taken from `source` / `path` in `claude plugin marketplace list --json` -- **`installPath` is never read as the effective root** (that one is the cache's copy; for a distribution that made a local directory into a marketplace, what's actually read is the real file in the work tree, and reading `installPath` instead would judge a correctly configured environment as FAIL). **`installLocation` is never taken as the material either**: on a `source:"directory"` element it merely repeats `path`, while on a `source:"github"` one it points into the marketplace cache under `~/.claude/plugins/marketplaces/<name>` -- on its own it can never say which real file is being distributed, so the check reads `source` first and only then `path` (only a `source:"directory"` element carries `path` at all). The judgment has five states, and only one -- "points at this work tree" -- reads green; the other four (pointing at a different location, no registration, not a local-directory distribution (`source` isn't `directory`), or unable to tell) are all FAIL.
- **A shape that can't be determined never reads green** (this covers, for example, the plugin-activation check in an environment where `claude plugin list --json` can't be read).
- **Installation and PATH are separate facets**: placing the symlink alone doesn't make the command runnable (macOS's default PATH has no `~/.local/bin`). A session being prompted to hand over, and the skill's own guidance, both run `rein` off PATH -- so for a lineage where the real file already matches, doctor checks resolution through PATH too (it skips this for a lineage that isn't installed at all, so the same fact never splits into two FAIL lines).
- **The usage writer is checked by whether a record matching the contract exists, not by whether the location exists** (never leaving a shape where merely `mkdir`-ing the location reads green). **The location not existing yet is a `WARN`, not a `FAIL`**: the one thing that creates it is the statusLine writer's `mkdir -p`, on the first turn of the first session opened after registering it, so for a fresh install that is the ordinary state with nothing to fix -- and the next stage of the same situation ("the location is there, with no record in it yet") already answers `WARN` carrying that same recovery, so reporting this one `FAIL` split one situation into two disagreeing answers and put a red line in front of every first `rein init`'s closing `doctor`. **The line between `WARN` and `FAIL` is drawn on whether the writer will be able to create it, never on whether the value was set explicitly or came from the default** (the default location is created by that same `mkdir -p`, so "explicitly set" on its own says nothing about whether it will work): something that is not a directory already sitting at the path, and a nearest existing ancestor that is not a writable directory, are both shapes `mkdir -p` fails on and no session will ever fix, and both stay `FAIL`. The record is checked **down to its type** too (`used_percentage` has to be numeric -- a string like `"20"` can't be folded as a number by the reader). When nothing is registered, a paste-in example is attached -- since `rein init` never rewrites settings, this is the only place that offers one.
- **statusLine passes or fails by whether a record matching the contract exists, not by whether it's the bundled writer**: a different writer is still OK as long as its record matches the contract (a correctly working configuration never keeps sounding an alarm). Registration identity is checked by **the real file's path**, so even a same-named registration reads WARN if it's a different checkout's real file (an update taking effect on only one side -- the same discipline as the installation symlink).
- **statusLine accepts broadly and stays safe**: the registration command's leading word is accepted whether it's quoted (`"..."` / `'...'`) or not, and an unquoted registration is never FAIL (this is **text the user writes into their own settings**, not something rein owns). The paste-in example, on the other hand, wraps the writer's path in double quotes -- since this command runs through a shell, omitting the quotes would word-split it for a repository placed at a path containing a space. **This is the opposite of how the hooks registry is treated** (that one is rein's own shipped artifact, so quoting is required there by a gate).
- **Accepting broadly stops at whether it's quoted -- handling `~` is the one exception, and it follows the shell.** `~/...` is expanded **only when it sits outside quotes**; a `~` inside quotes (the shape `"~/scripts/rein-statusline.sh"`) is left unexpanded, because that's how a shell actually treats it -- this registration never really runs. Accepting broadly here too would **report a registration that never runs as green, "the bundled writer is registered"** -- exactly the inverse of what this check is meant to catch (registered but not running). A registration that never runs is never reported green: it is reported as FAIL by name, saying that the shell never expands a `~` inside quotes, so this registration does not run, and to rewrite `~` to an absolute path and quote it (folding it into the same reason text as other shapes whose real file can't be resolved would produce the wrong reason, "a different writer is registered," leaving no way to tell what to fix).
- It warns when the last firing is more than a day old. The reasoning behind that window, and why an anomaly in the fire log is a WARN, are in [the hooks specification](hooks.md).
- Detecting forced isolation is FAIL -- it runs the same judgment `up` does (never leaving a shape where the diagnostic passes an environment and only the launch fails there; the three paths sharing this judgment are in [the locations and locks specification](runtime.md)).
- Every line starts with one of three: `OK` for satisfied, `FAIL` for not satisfied, `WARN` for something the user needs to look at and decide. **`doctor` exits non-zero if even one line is `FAIL`** (a `WARN` never fails it). **Every line, with nothing loose between them**: a shared-library predicate that names its own rejection by printing to stderr (the form its callers inside `$( )` need) is silenced at `doctor`'s own call site wherever `doctor` already reports that same reason on a line of its own -- otherwise the identical sentence lands twice, once as a raw line belonging to no section. Only that one call site is silenced; every other caller still gets the reason.

## Structural limits on what `prune` scans

Because this is an irreversible delete, **the scan's scope itself is closed off structurally.** How the flags choose a kind and a target is in `rein help`; the canonical source for the orphan scan root and its cutoff constraints is [the locations and locks specification](runtime.md).

- `session` candidates are drawn from the handover log, and only ones satisfying all five conditions: not currently pointed at; **the handover from that generation is confirmed by `handover_completed`**; older than the current generation; finished; and a short job ID can be looked up for it.
- If the current pointer can't be validated, the whole `session` scan fails -- this never proceeds without being able to read the one input that names who must not be deleted.
- For `archive` (old material archived under `processed/`, `rejected/`, `cancelled/`), the age floor for candidacy is the `archive_days` setting (default 30 days -- older than that is a candidate), and it's **included in the default scan** (since nothing actually disappears without `-f`, including it in the default scan never becomes "silently deleted").
- For `child` (entries in the children ledger, `<runtime>/children/<session_id>.<agent_id>`), a candidate is an entry belonging to a `session_id` **other than the one the current pointer names**, and it's **included in the default scan** for the same reason `archive` is -- the scan and the delete both stay inside this lineage and touch only plain files. **The current session's own entries are never candidates**: removing one would let a handover go out while that session's child is still running, which is the very thing the ledger exists to prevent (see "Runtime data hooks use" in [the locations and locks specification](runtime.md)).
  - **A pointer that can't be validated, or isn't there at all, makes this scan produce nothing, and the reason is shown.** The pointer is the only input naming which session's entries must be kept. Unlike the `session` scan this doesn't fail the whole run: the kind sits in the default scan, so failing here would take a plain `rein prune` down with it on a lineage that has yet to hand over even once.
  - It is **housekeeping only and never changes a judgment** -- entries belonging to other sessions are already inert, because every reader looks only at its own `session_id`'s entries.
- The default scan covers `archive` and `child`, and `-o` / `-s` / `-a` add more. `claude agents --json --all` is never read unless `session` is chosen, so other kinds still work in an environment where enumeration can't be read.
- `-f` re-checks preconditions right before deleting each candidate, and deletes it under the target lineage's own operation lock.
- **The candidate count also appears in `rein status`'s `cleanup candidates` line**, run through the same one implementation `prune` uses to count -- keeping it in two places would let status say "0" while `prune` lists candidates behind its back. **A kind that can't be counted reports a reason, not a fallback to 0** (`session`: enumeration can't be read; `orphan`: a cross-lineage scan doesn't make sense for a lineage with an explicit location; `child`: the current pointer can't be validated). Enumeration reuses **the same one call** the primary session's liveness check already made (one status run never hits an external command twice).
